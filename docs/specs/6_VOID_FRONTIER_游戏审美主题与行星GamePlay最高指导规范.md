## 0.3 必须明确废止的方向

以下做法不再允许作为正式地表体验的最终方案：

- 不得把行星地表主体表现为由大量可见立方体组成的方块地形。
- 不得把 `64×24×64` 体素网格、Greedy Meshing 和 DDA 体素拾取当作未来地表视觉与交互架构的不可替代基础。
- 不得仅通过修改 `CATEGORY_TERRAIN.tint`、天空渐变或几组 RGB 数值，就宣称完成了一个新的行星主题。
- 不得以“随机高度图 + 随机散布几个模型”代替登陆任务关卡设计。
- 不得让任务目标、撤离点、关键通道、掩体、桥梁、遗迹入口等任务关键结构完全依赖无约束随机生成。
- 不得让所有星球共享同一地貌，只靠色相区分。
- 不得为了追求地形自由改造而牺牲任务可读性、寻路可靠性、碰撞稳定性、存档确定性和长期性能。

## 0.4 本文档不意味着什么

“改用三角化地形”不等于要求所有地表都使用高密度、每帧重建的 Delaunay 网格；“类似《戴森球计划》的感觉”也不等于复制其专有 UI、机甲、建筑模型或材质。

本文档要求的是：**连续、自然、具有大尺度地貌轮廓的三角网格地表；具有明确工业尺度、可读资源节点和建造空间的行星场景；以及能把主题美学转化为具体行动、资源与任务选择的完整玩法。**

参考作品只作为设计语言和体验范式来源。不得复制其受保护的角色、建筑外形、名称、剧情、美术资产、Logo 或 UI 版式。所有最终视觉资产必须原创并由本项目的程序化生成或自制几何/材质实现。

# 1. 核心产品愿景：每颗星球都是一个有身份、有地貌、有故事、有用途的世界

## 1.1 一句话定义

**VOID FRONTIER 的每一颗可登陆行星，都必须像一个独立的异星目的地：从轨道上就能辨认它的视觉身份，着陆后能感受到它独特的地质与气候，在地表能找到被设计过的任务地点，向外围探索时又能进入可持续扩展的程序化世界；玩家对它采取的行动必须改变世界状态，并回写到探索、科研、殖民、工业、贸易或叙事系统。**

## 1.2 玩家应该产生的感受

玩家第一次看到一颗星球时，不应只想：“这是一颗冰星，温度 -80 度。”而应该产生更具体的判断：

- “这是一颗被深海覆盖的星球，海面下有巨大遗迹和蓝色发光生态，我要找潜航器或深潜装备。”
- “这是一颗永冬星球，开阔冰原里有唯一的热源塔，热量分配就是任务路线和生存资源。”
- “这是一颗干燥的极夜星球，黑色地表上铺着白色盐晶，紫色极光掠过天空，热源和导航比食物更关键。”
- “这是一颗硫雾沼泽星球，绿色气体从地裂口喷出，低洼处危险，但也是化工和稀有气体的重要来源。”
- “这是一颗生态极其旺盛的世界，夜间树冠和生物脉络会发光，资源不是简单矿石，而是活体生态与共生材料。”
- “这是一颗熔岩星球，安全路径不是平地，而是高架黑曜石桥、玄武岩脊线与冷却平台组成的垂直交通网。”

**每个主题都应该让玩家立即明白：这里为什么特别、这里危险在哪里、这里能获得什么、这里值得做什么。**

## 1.3 Dyson Sphere Program 式行星感：采用体验特征，不复制表面形式

“类似《戴森球计划》的感觉”应准确理解为以下体验组合：

1. **星球是一张有大尺度地理连续性的真实空间画布。** 地形不是一堆离散方块，而是从山脉、盆地、平原、峡谷、海岸线到平台的连续地貌。
2. **玩家能直观理解空间与工业布局。** 资源在哪、建筑放哪、道路怎么走、物流如何转弯、地形是否挡路，都能从画面上直接读出来。
3. **行星地理决定经营和建设方式。** 平坦区域适合工厂阵列，陡坡适合采矿或观测设施，水域适合海上平台，极端环境要求隔热、气密、抗腐蚀等专用设施。
4. **世界表面具有明确尺度。** 一座发电站、一条管线、一座桥、一片矿区、一座前哨在空间上有可感知的大小和位置，不是图标贴纸。
5. **从探索到建设有连续关系。** 玩家先认识地貌、资源与风险，再选择建设方式；建设又改变地表和后续行动路线。
6. **视觉是服务于操作的。** 远景能看出地貌轮廓，中景看得清资源区和设施，近景能执行角色行动与交互。

这不是把所有玩法缩成生产线。VOID FRONTIER 仍保留第三人称小队行动、地表任务、异常调查、殖民经营和星际战略。工业建设是行星玩法的重要一环，但不是唯一玩法。

## 1.4 正式视觉原则

| 原则 | 必须达到的结果 | 禁止的退化形式 |
|---|---|---|
| 连续地貌 | 地表轮廓自然，山脊、河谷、坡面和海岸过渡连续 | 方块台阶、棋盘格山体、无意义随机噪点 |
| 主题识别 | 远景轮廓、主色、天空、材质和地标共同指向主题 | 仅更改天空颜色或地表 Tint |
| 空间可读 | 玩家能判断坡度、危险区、道路、资源和任务方向 | 关键地形与交互目标混成一片 |
| 人工设计 | 登陆任务核心区域有明确构图与路线设计 | 纯随机出生点和随机摆件 |
| 程序化延展 | 核心任务区以外可以持续生成有变化但合理的地貌 | 无限空地、重复贴花、周期性复制地形 |
| 玩法驱动 | 主题改变移动、采集、战斗、建造或经济决策 | 只有漂亮背景，没有可交互机制 |
| 光照可信 | 太阳方向、天空散射、雾、湿润度和自发光相互协调 | 所有星球统一打光、统一雾色、统一反射 |
| 工业融入 | 建筑、管线、桥梁与自然地形形成合理空间关系 | 建筑漂浮、埋入地形、道路悬空或断裂 |

# 2. 地表技术方向：从方块体素转向连续三角网格地形

## 2.1 目标几何表示

正式地表的主几何应改为 **Triangulated Planetary Terrain（三角化行星地形）**。它以连续高度场、地质边界、坡度、侵蚀结构和人工地标为输入，生成带有顶点位置、三角索引、法线、切线、材质权重和语义属性的三角网格。

这里的“三角化重建”不是要求整张星球用纯 Delaunay 三角剖分一遍，而是一个分层组合：

- 大尺度地形：由确定性高度场/地貌场构成。
- 基础采样：规则或分层采样的顶点格网，按一致的三角绕序生成索引。
- 自适应简化：根据地形曲率、屏幕误差、坡度、任务关键性提高或降低三角密度。
- 不规则局部结构：海岸、悬崖边缘、裂隙、山脊尖端、人工地标边界等可使用受约束 TIN / Delaunay 类细化。
- 地表装饰：岩石、植被、晶体、残骸、管线和建筑是独立网格/实例，不再靠把地表拆成方块表达。

**首期推荐方案：规则高度场三角网格 + 局部自适应细化 + 任务区约束网格。** 这是比一开始实现全局复杂 TIN 更可控的起点。`mapbox/delatin` 可作为“对高度场做 Delaunay 网格简化并用最大误差控制顶点数量”的算法参考，而不是必须引入的第三方运行时依赖。[Delatin 技术说明](https://github.com/mapbox/delatin)；其核心思想是以给定最大高度误差控制三角网格细化。[^1]

## 2.2 世界尺度与坐标体系

地表不再以“64×64 个方块格子”作为最终空间表达。建议采用以下坐标层：

| 坐标层 | 表达范围 | 用途 |
|---|---|---|
| Planet Local | 行星局部切平面或 cube-sphere 面片上的坐标 | 地形生成、顶点、建筑落位、碰撞与地表导航 |
| Site Local | 登陆点/任务场景的局部坐标 | 人工关卡、任务目标、撤离区、道路和掩体 |
| World / Entity | 稳定实体 ID 和世界坐标映射 | 存档、POI、资源节点、单位和命令引用 |
| Render Camera | 相机相对坐标 | 高精度近景渲染，避免远距离浮点抖动 |

首期地表可以先使用局部切平面三角高度场，保证可玩性和视觉质量；后续若要实现从轨道到地表的更大尺度连续过渡，再引入 cube-sphere + quadtree chunk。不得把局部切平面实现误认为最终整个行星只能是一块平板。

## 2.3 推荐地形数据模型

一个 `TerrainChunk` 不再保存“每格一个实体材质 ID”，而是保存如下结构（示意，字段可依工程规范调整）：

```js
{
  id: "chunk_x_y",
  planetId: "planet_xxx",
  seed: 123456,
  lod: 0,
  bounds: { minX: 0, maxX: 256, minZ: 0, maxZ: 256 },
  vertices: {
    position: Float32Array,
    normal: Float32Array,
    tangent: Float32Array,
    materialWeights: Uint8Array,
    biomeId: Uint8Array,
    flags: Uint16Array
  },
  indices: Uint32Array,
  sourceRevision: 1,
  meshRevision: 1,
  dirty: false
}
```

`materialWeights` 可以编码多种材质的混合权重；`biomeId` 表达生态/地质区域；`flags` 用于道路、建筑地基、任务区边缘、不可破坏区域、危险表面、可采资源等语义标记。

地形网格是表现和碰撞的共同来源，但不意味着把 WebGL Buffer 直接写进存档。存档应保存确定性生成参数、玩家编辑操作、被采掘/破坏实体状态和必要的高度场差异；网格可在加载时确定性重建。

## 2.4 网格生成与细分规则

地形生成至少分成以下步骤：

1. 生成宏观地貌场：大陆/海盆、山脉走向、陨石坑、裂谷、火山、冰川、盐湖、峡谷等。
2. 叠加中尺度地貌：山脊分叉、支谷、风蚀槽、沙丘、冰裂隙、熔岩流堤岸、珊瑚礁等。
3. 计算顶点属性：高度、坡度、曲率、湿度、温度、侵蚀量、地表类型、矿脉影响和生态适宜度。
4. 根据几何误差细分：高曲率、高坡度、任务关键地标、角色活动区和镜头近处优先细化。
5. 对三角形索引执行一致绕序；计算/平滑法线，必要时保留硬边法线。
6. 生成材质权重和地表贴花。
7. 建立碰撞与导航加速结构。
8. 按 chunk 上传 GPU，并保留可回收 CPU 数据。

规则格网三角化时必须消除明显的单一对角线纹理：采用交替对角线、基于局部曲率的对角线选择或局部受约束三角化；不得形成从远处就能看见的规则斜线网格。

如果局部使用 TIN 简化，必须设置最大几何误差，并让任务区、地标轮廓、悬崖边、桥梁落点和建筑地基边界进入约束点集合，不能为了减少三角形而抹平任务关键结构。Delatin 的最大误差控制是可参考的一个具体方向。[^1]

## 2.5 行星级 LOD 与无缝拼接

对大型地表区域，不得一次性把全星球最高精度顶点全部常驻内存或逐帧重建。推荐采用分块 LOD：

- 近景：角色周边、任务地点、地标和建筑使用高精度三角网格。
- 中景：以较粗网格表达坡面、沟谷、道路和建筑群轮廓。
- 远景：仅保留大尺度高度变化、山脉轮廓、海岸线和地标剪影。
- 视锥外：暂停细节更新；必要时保留低成本碰撞或导航数据。

相邻 LOD 不能出现裂缝、跳变和明显 Pop。可以采用几何 Morph、过渡环、边缘 Skirt、共享边界顶点或 clipmap 过渡方案。NVIDIA GPU Gems 对 Geometry Clipmaps 的描述强调嵌套网格、屏幕空间三角形尺寸、过渡区域 morph，以兼顾平滑切换和 watertight mesh；本项目可以吸收这种思路，而不是机械照搬其地球高度图示例。[^2]

若采用 cube-sphere quadtree，应对六个球面分区之间的边界、极区畸变、LOD 邻接关系和法线连续性单独测试。若采用局部切平面方案，必须定义其世界半径、地平线和地图边缘处理，不能在镜头边缘突然看到平板截断。

## 2.6 材质系统：连续混合，而不是每个三角形一块纯色

材质混合必须由地形语义和环境参数驱动，至少考虑：

- 高度（海岸、低地、山顶、雪线、熔岩平台）。
- 坡度（岩壁、碎石坡、土壤坡、可建造平台）。
- 温度（积雪、冰层、冻土、灼热地表）。
- 湿度/水分（泥地、盐碱、潮湿岩面、植被）。
- 化学环境（硫沉积、酸蚀、玻璃化表层、腐蚀结壳）。
- 地质层（表土、沉积岩、玄武岩、晶体、黑曜石、金属结构）。
- 生物覆盖（苔毯、菌毯、珊瑚、根系、发光生态膜）。

材质边界应有自然过渡和可识别的地质层次。近景可以使用程序化 triplanar mapping / world-space projection，避免 UV 拉伸；没有外部贴图时，使用 Shader 噪声、分层色带、微法线和程序化纹理实现。禁止把大面积表面简化成重复棋盘格。

颜色配置应以 sRGB 设计色为输入，渲染前转换为线性空间；不要把十六进制 sRGB 数值直接当线性光照数值相乘。HDR/Bloom、ACES 或既有后处理方案应保持颜色一致，不能为了“更亮”造成主题色全部过曝。

## 2.7 与体素系统的兼容迁移原则

现有 `SurfaceSandbox.js`、`PlanetSurface3D.js` 及 `GroundView.js` 已经包含体素地形、矿脉、DDA、角色碰撞、挖掘/建造等路径。**允许过渡期保留离散数据用于任务规则、资源状态或旧存档兼容；但禁止继续把方块外观当作正式地表。**

迁移方式：

- `GroundMission.js` 的任务状态机、目标计数、奖励幂等、战斗规则可以保留。
- 玩家旧的地面任务二维坐标可以通过稳定的 SiteTransform 映射到三角地形局部坐标。
- 旧矿脉体素数据可以迁移为资源节点/资源密度场/地下沉积层记录；不能继续要求地表出现可见矿石立方体。
- 旧的 `digVoxel` 应逐步替换为 `ExtractResourceNode`、`ModifyTerrainSurface` 或 `MineDeposit` 等语义操作。
- 原 DDA 体素拾取应替换为相机射线与三角网格求交（BVH / chunk AABB / heightfield traversal），或对特定体积资源使用独立体积拾取。
- 体素地形建造应迁移为网格表面投影、地基/墙体/模块化结构网格、道路样条和局部地形整形。
- 老存档应通过 schema migration 保留 POI、采掘成果、任务结算和资源数量；不要求把所有旧体素精确还原成新地貌，但迁移必须有可解释规则并留存旧世界 seed。

不得一口气删除旧模块后再慢慢补功能。应保持旧任务/存档可读，在新网格垂直切片验收通过后逐步转移调用。

# 3. 当前地表渲染故障：必须先建立可靠的每帧状态契约

本章针对用户当前报告的两个明显故障：地形表面像被背面剔除一样消失，天空/背景出现残影和重复拖影。它们是 P0，必须在新地形大改前单独诊断并修复，不得把它们带进新 Mesh Renderer。

## 3.1 已经确认的代码事实

审阅基线 `2d471a5e35db4fb8f9cb5b58d3fcb79dbedff9d2` 的源码后，确认：

1. `SurfaceSandbox.js` 当前地形是 `64×24×64` 的 voxel height volume，以 Simplex/fBm 生成高度、洞穴和矿脉。
2. `PlanetSurface3D.js` 把体素外露面经 `greedyMeshChunk()` 合并为三角面片，地表可见轮廓仍然继承体素高度层级。
3. `PlanetSurface3D.draw()` 在每帧开始处清除 `gl.DEPTH_BUFFER_BIT`，随后关闭深度测试、绘制天空全屏三角形，再恢复深度测试；该位置没有显式清除场景颜色缓冲。
4. `PostProcessor.beginScene()` 绑定场景 FBO 并设置 viewport，但没有在该方法内完成颜色/深度清除。
5. `CanvasManager.beginFrame()` 当前确实会清除 HUD 2D Canvas，因此不能把旧版本“HUD 没清屏”的问题直接当作当前版本的确定根因。

## 3.2 背景残影：显式清色，禁止依赖“天空恰好覆盖所有像素”

当前渲染路径依赖天空全屏三角形覆盖整张 FBO，以间接覆盖上一帧颜色。这种做法不应成为渲染正确性的唯一保证。只要 viewport、scissor、colorMask、shader 分支、帧缓冲绑定或其他 GL 状态出现偏差，就可能残留上一帧颜色；新增水体、天空雾、分层 pass 或局部渲染后，隐式依赖更加脆弱。

**必须落实的每帧契约：**

1. 在场景 FBO 绑定后立即设置正确 viewport。
2. 显式设置 `gl.colorMask(true, true, true, true)`。
3. 如不使用 scissor，显式关闭 `gl.SCISSOR_TEST`；若使用，必须在清除前设置覆盖目标范围的 scissor。
4. 设置主题天空/地平线的 clear color。
5. 执行 `gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT)`；如后续启用 stencil，再纳入 stencil clear。
6. 再执行 sky pass、terrain pass、water pass、opaque objects、transparent effects、HUD composition。
7. 每个 pass 必须声明并恢复其 blend、depth test、depthMask、cull、frontFace、polygon offset、framebuffer 和 viewport 状态。
8. `endScene()` 合成完成后回到默认帧缓冲，不能把临时 FBO 或错误 viewport 留给下一帧。

可以在 `PostProcessor.beginScene()` 统一做 FBO clear，或由每个场景 Renderer 在 `beginScene()` 返回后负责，但必须只有一个明确所有者并写入注释与测试。不得出现两个 Renderer 各自假设对方已经清屏的情况。

**注意：** 当前没有浏览器运行时复现记录，不能只凭代码缺少 color clear 就宣称已唯一解释全部残影。显式清色是确认存在的健壮性缺陷；如果修复后仍有拖影，继续检查 viewport/scissor、shader discard、FBO 绑定、透明混合、HDR 合成和 HUD 重复绘制。

## 3.3 地形消失/疑似背面剔除：按证据链诊断

禁止直接在正式版本中永久 `gl.disable(gl.CULL_FACE)` 作为未经验证的最终方案。应按以下顺序定位：

### A. 记录实际 GL 状态

在调试入口中记录：

- 当前绑定 FRAMEBUFFER 与实际附件尺寸。
- `VIEWPORT`、`SCISSOR_BOX`、`SCISSOR_TEST`。
- `CULL_FACE` 是否启用、`CULL_FACE_MODE`、`FRONT_FACE`。
- `DEPTH_TEST`、`DEPTH_FUNC`、`DEPTH_WRITEMASK`。
- `COLOR_WRITEMASK`、`BLEND`、blend equation/factors。
- draw 前后的 `gl.getError()`；关键资源的 VAO、VBO、index/vertex count 是否大于 0。

### B. 三种诊断渲染模式

1. **无剔除模式：** 暂时关闭 `CULL_FACE`，使用纯色 Unlit shader 绘制地形。若正反面都可见，说明需继续检查绕序、frontFace 或 pass state；不能据此认为几何本身正确。
2. **线框/法线模式：** 输出三角网格边线、法线方向和每个 chunk 颜色。检查法线反向、索引错误、三角形退化和 chunk seam。
3. **单三角形朝向测试：** 从已知朝上的地面三角形构造测试面，计算 `(v1-v0) × (v2-v0)`，并与预期外法线点积；要求朝外面点积为正。对所有六个方向/边界拼接单元执行测试。

### C. 正式状态契约

- 明确项目使用 CCW 还是 CW 作为正面；推荐统一 `gl.frontFace(gl.CCW)`。
- 完成网格绕序与法线测试后，对不透明 terrain 可启用 back-face culling 作为优化。
- 天空全屏三角、双面薄片、水面透明层、某些粒子/特效应按各自材质策略禁用剔除。
- 每个 pass 不得依赖上一个 pass 留下的状态；进入 pass 时显式设置需要的状态。
- 如果地形需要双面材质，应单独标记，不允许简单地将整个场景永久关闭剔除。

### D. 相机、出生点和深度检查

同时检查：角色出生点是否位于三角地形之上；相机眼位是否被地表或天空盒遮挡；近远裁剪面是否合理；地形坐标与相机坐标是否有轴向/单位混用；地形是否实际被提交绘制；绘制顺序是否让地形被天空或后处理覆盖。

## 3.4 P0 修复验收

- 从同一存档进入地表，持续旋转相机 360°、缩放、快速移动、穿越不同 LOD 区域，不能出现历史帧重影。
- 在固定种子下，从天空、远景、坡面、凹地和地表近景检查地形全部正确渲染。
- 无剔除诊断与 CCW 正式剔除两种模式得到一致的正面可见结果，背面按设计被剔除。
- WebGL context lost / restored 后，地形、天空和 HUD 全部恢复，不产生旧帧残留。
- 连续 10 分钟相机运动，画面没有累积拖影；Console/GL error 无未解释错误。
- 保存渲染诊断 JSON：浏览器、GPU、GL 状态、viewport、FBO、地形顶点/三角形数、chunk 数和截图路径。

# 4. 行星主题系统：Planet Theme 是完整的世界身份，不是一个颜色字段

## 4.1 主题定义

每颗行星必须绑定一个主主题（`primaryThemeId`），可选 1–3 个次级地貌/生态修饰器（`secondaryThemeModifiers`），形成视觉、环境、玩法和资源的共同身份。

一个主题必须至少覆盖以下九个维度：

1. **主轮廓（Silhouette）：** 从轨道上看得到的云带、冰盖、海盆、山脉、裂缝、浮岛或环状结构。
2. **地貌结构（Geomorphology）：** 山脊、峡谷、盆地、海岸、台地、熔岩河、盐壳、冰裂隙等。
3. **主材质（Surface Materials）：** 岩、砂、冰、盐、晶体、珊瑚、菌毯、玄武岩、玻璃化硅质层等。
4. **主色和强调色（Palette）：** 至少定义基色、阴影色、高光色、危险色、自发光色和大气色。
5. **光照与天空（Lighting / Atmosphere）：** 太阳色温、散射、雾、星空可见度、极光、云层、尘暴、日夜差异。
6. **动态环境（Weather / Motion）：** 风、潮汐、气体喷涌、沙暴、冰尘、火山灰、磁暴、浮游颗粒等。
7. **生态/结构地标（Landmark Grammar）：** 一眼可辨的植物、地质或人工结构轮廓。
8. **危险与行动规则（Gameplay）：** 温度、压力、腐蚀、能见度、地面稳定性、潮汐窗口、磁干扰、氧气等对操作的实际影响。
9. **资源与经济钩子（Economy）：** 该世界为什么值得探索、建设或争夺；资源必须进入生产链或科技系统。

只完成前五项属于视觉主题原型；要成为正式主题，九项必须都有定义，并至少有一个真实玩法闭环。

## 4.2 主题一致性规则

主题色不是简单给 Terrain shader 的 `uTint`。一个海洋主题必须拥有水深、波面、海床、海岸线、生物光、潜水能见度和海底结构；一个永冬主题必须拥有雪线、冰层、风雪、结霜、热量设施与保温玩法；一个熔岩主题必须有熔岩河/岩浆池、黑曜石冷却边缘、热辐射和高架通路。

如果主题换成另一套颜色，其他所有几何、环境、互动、资源和玩法也完全不变，则视为主题设计失败。

## 4.3 主题分层与生成权重

`planet.category` 继续描述宏观天体/环境分类（rocky/ocean/ice/desert/gasGiant/lava/toxic/artificial 等）；`themeId` 描述本次生成的具体艺术与玩法身份。两者不是同一个字段。

- `category` 决定登陆物理可行性、基础环境和大类生成约束。
- `themeId` 决定视觉语言、地貌语法、POI 组合、特殊环境机制和场景资产套件。
- `secondaryThemeModifiers` 负责增加次级特征，例如“永夜 + 晶体风暴”“海洋 + 硫化喷口”“沙漠 + 远古巨构”。

主题必须服从基础天体参数，不能让一颗高温无水熔岩行星被随机赋予海洋主题。主题抽选应基于恒星类型、轨道带、温度、重力、大气、水储量、辐射、磁层与资源配置，并用独立派生 RNG 子流生成，不能改变既有世界主 RNG 的消费顺序。生成器应设置权重、兼容约束、稀有主题概率和星系级多样性约束，避免相邻行星反复出现相同主主题。

## 4.5 主题详细规范

### 4.5.1 碧渊海洋 `abyssal_ocean` — 不是一张蓝色地面贴图，而是一个垂直分层的水世界

**视觉印象：** 远处是连续的深蓝海面和大片云影；近处能看到巨浪、海雾、浪花和深浅分界。海面以下，浅海是透亮的青绿，深海逐渐变成蓝黑；珊瑚塔、古代穹顶、巨型礁柱和海底裂谷在不同深度形成空间层次。夜间有生物光脉络，远处的发光生物群像城市灯火一样在黑暗中闪烁。

**亚特兰蒂斯 + 娜迦式感受的正确转译：** 重点不是给人类模型换蓝皮肤，也不是照搬某个 IP 的娜迦造型；重点是“文明从海洋环境中自然生长出来”。城市要有垂直分层、巨型珊瑚/贝壳/骨质结构、流线型水下通道、发光导航和海沟边缘的仪式性地标。可设计原创的两栖/水生智慧种族，其服饰、工具、建筑和移动方式都适应水下生活；生物轮廓可以借鉴鳍、鳞、触须、壳甲等自然形态，但必须是全新物种设计。James Wan 对《Aquaman》世界构建的访谈特别强调了水下文明应以不同于陆地建筑的逻辑生长，甚至提出珊瑚式生长建筑的概念；这比单纯“蓝色海底城”更值得借鉴。[^7]

**地形结构：** 海盆、海沟、海台、珊瑚礁脊、海底热泉、海底洞穴、沉没城区、海岸平台。海床不是平底；应有坡度、沙脊、沟谷和岩礁。

**环境效果：** 水下视距随深度缩短；不同 RGB 波段按路径吸收，太阳光随深度衰减；海床有动态焦散光斑，水中有稀疏悬浮颗粒（Marine Snow）；表层有波浪反射、浪花和海雾。POSIM 的公开水下渲染文档把水路雾、RGB 吸收、深度阳光衰减、海床焦散和悬浮颗粒分别列为效果层，适合作为技术拆解参考；NVIDIA GPU Gems 对实时焦散给出程序化近似方案。[^3][^4]

**可玩内容：** 潜航器下潜、压力舱、氧气/电量管理、海底遗迹调查、珊瑚样本采集、海床矿脉、潮汐开闭通道、海底运输平台。玩家可以在浅海建立漂浮基地，在深海建立耐压设施。

**标志性任务地标：** 半埋海底穹顶、断裂的海神塔、长满珊瑚的巨大机械环、海沟边缘的蓝色信号柱。

**危险：** 水压、洋流、能见度下降、深海生物、周期性巨潮、海床热泉。

### 4.5.2 永冬炉境 `permafrost_furnace` — 冷世界中唯一的暖色是玩家争夺的生存资源

**视觉印象：** 巨大的蓝白冰原、冰崖和冰裂缝占据主体；天空低沉，风雪沿地面横向扫过。远处出现一座橙色热源塔，周围形成小片暖光聚落。暖色不是装饰，而是热量网络覆盖范围的可视化。

**地形结构：** 冰川盆地、冰脊、裂隙、雪堆、冻湖、冰洞、风蚀裸岩。

**玩法：** 热量管网、燃料采集、基地保温、人员冻伤、冰层钻探、暴风雪前的撤离窗口。热源塔/发电站的运行状态应在画面中可见；基地边界由热区和安全区构成。

**Frostpunk 式核心不是“雪很白”，而是“热量具有空间分布与社会后果”。** 热源覆盖范围、建筑隔热等级、居民工作位置、燃料储备和暴风雪预警应直接影响行动与生存；离开热区去搜寻资源就是一次有风险的任务。Frostpunk 官方商店说明将“heat means life”作为核心规则，并把热量、基础设施、资源和探索放在同一个生存决策系统中。[^8]

**标志性任务地标：** 被冰封的通信塔、裂谷上的加热桥、半埋在雪坡里的前哨站、被风雪切断的输热干线。

### 4.5.3 赤砾边疆 `red_regolith_frontier` — 不是普通沙漠，而是可开采、可建设的行星荒原

**视觉印象：** 熟褐色砂岩、铁锈红土壤、浅金色沙尘和远处低矮台地。太阳硬朗，天空干燥，地平线清楚；风尘掠过山口时形成连续的尘幕。

**地形结构：** 砂岩桌山、风蚀沟槽、陨石坑、干涸河床、裸露矿脉、岩壁平台。

**玩法：** 水冰勘探、太阳能阵列、风能、矿区布点、地下水井、风暴防护、低压大气设备。矿区和基地建设应该自然贴合台地和峡谷。

**标志性任务地标：** 崖边旧采矿平台、深井水塔、失联探测车、巨型砂岩拱门。

### 4.5.4 永夜晶荒 `dry_night_polar` — 极夜但不下雪，避免与冰冻主题混为一谈

**视觉印象：** 地表以黑蓝色岩土和白色盐晶覆盖，地形干燥、脆硬，天空长期处于深夜；紫色极光或高空电离带横跨地平线。白色地貌像骨骼一样突出，紫色只用于天空、晶体和特殊能量。

**地形结构：** 黑色岩台、白盐盆地、干裂平原、晶体脊、浅层地下热泉、陨坑。

**玩法：** 极夜导航、热储能、地热井、低温设备维护、雷达/星敏感导航、盐晶提炼。玩家必须在黑暗中依靠信标、反射和热成像识别路径。

**区别规则：** 不得大量生成普通积雪和冰川；它是干燥极夜世界，不是 `permafrost_furnace` 的换色版本。

### 4.5.5 硫雾沼泽 `sulfur_marsh` — 美丽但危险的化学地貌

**视觉印象：** 暗绿、硫黄、酸性荧光绿为主。地表有泥浆气泡、硫磺结壳、酸池和喷气孔；低空覆盖贴地毒雾，远处有高耸的黑色岩柱。绿色不能像普通森林一样温柔，应带有腐蚀、毒性和不稳定感。

**玩法：** 防腐服、过滤器、气体采集、硫化物/挥发物精炼、喷口定时封堵、风向判断、低洼区域绕行。气体口可以既是危险源，也是资源源。

**大气身份必须明确：** 这不是普通的绿色沼泽，也不是可以自由呼吸的潮湿丛林。地表低空长期滞留硫化/酸性气体，低洼区域会形成可见的毒气湖；开阔高地也可能被周期性气体喷发覆盖。可见植被应稀少、耐化学腐蚀，主要生命形态可以是微生物膜、矿物菌落或隔离生态舱。现实火山喷气孔可释放二氧化碳、二氧化硫等气体，并在周边形成硫、硫化物和其他矿物沉积及强烈热液蚀变；这一点可作为“危险与资源同源”的世界构建依据。[^9]

**地标：** 巨型喷气锥、被腐蚀的钻井站、酸池上的耐腐蚀高架管桥、毒雾中的失联气象塔。

### 4.5.6 星辉生物圈 `biolume_canopy` — 生态本身就是地形、灯光与资源系统

**视觉印象：** 白天是蓝青色大气、紫色山影和高耸的异星林冠；夜晚植物、菌丝、动物迁徙线和水体发光。地表有瀑布、根系桥、巨叶、树冠平台与发光孢子雨。

**玩法：** 生物采样、生态链识别、共生材料采集、危险物种回避、生态修复、可再生生物质。某些资源只有在特定昼夜/天气窗口出现。

**生态规则：** 每一种可见发光物种应有明确的生态或任务意义，不能把整张地图铺满无意义发光装饰。

Avatar 官方世界资料将 Pandora 描述为包含广阔海洋、丛林、平原、山地和夜间生物荧光的多生态世界；本项目只借鉴“生态系统具有整体视觉身份”和“夜间生态发光”的方法，不复制原作生物和造型。[^5]

### 4.5.7 黑曜熔海 `obsidian_lava` — 让地表路线本身成为工程问题

**视觉印象：** 深黑玄武岩和黑曜石构成地表骨架，红橙色熔岩河在低谷中流动。山体高耸、山脊尖锐；桥梁与平台架在熔岩上方。亮区必须克制，熔岩发光不应冲毁整个画面对比度。

**玩法：** 热辐射、耐热装甲、地热能、桥梁承载、冷却管线、熔岩喷发周期、热源封堵。玩家应通过高架路径穿越熔岩区；某些桥梁需要抢修才能通行。

**标志性结构：** 黑曜石拱桥、玄武岩柱阵、悬空钻探平台、岩浆河上的热能转换站。

### 4.5.8 棱镜晶原 `prism_crystal` — 用几何折射制造可辨认的景观，而不只是彩色水晶

**视觉印象：** 大型晶体像山峰一样从地表生长，峡谷内部有折射光带，晨昏时晶体投射的彩色光斑会缓慢移动。远景轮廓应尖锐而有秩序。

**玩法：** 晶体共振扫描、折射光路谜题、矿脉采收、晶体结构稳定、能量谐振设备部署。大型晶体可能挡住无线电或改变导航仪器读数。

### 4.5.9 镜盐荒原 `salt_mirror_desert` — 极简、空旷、反射强烈的视觉世界

**视觉印象：** 白盐壳、浅粉色尘土和远处灰紫色岩山。地表开阔，天空和地表形成近乎镜像的低频反射；但不要让屏幕全白过曝。

**玩法：** 卤水提取、镜面聚光、蒸发池、盐壳下的水层调查、强反光造成的光学测距误差。

### 4.5.10 甲烷雾海 `cryomethane_sea` — 液态烃类海洋与极寒冰岸

**视觉印象：** 暗青色液态甲烷海、冷雾、蓝绿色冰岸和冰脊。海面反射更暗、更厚重，不像地球海水；远方雾带与浮冰轮廓形成低对比层次。

**玩法：** 低温燃料提取、烃类精炼、浮冰航道、耐寒船体、冰层裂缝和海岸平台。海面和碧渊海洋主题必须能一眼区分。

### 4.5.11 晨昏环带 `tidal_lock_dusk` — 用一颗星球呈现两个世界之间的边界

**视觉印象：** 潮汐锁定行星一侧永昼、一侧永夜，中间存在狭长晨昏带。昼面有强烈热亮，夜面有深冷蓝黑，暮光带由金色和蓝青色交汇构成。

**玩法：** 基地必须沿可居住的温度带布局；能源、冷却和物资需要跨温区运输；某些资源只在昼侧或夜侧出现。行星视图需将晨昏带作为一条显著地理结构呈现。

### 4.5.12 云海浮岛 `cloud_giant_atolls` — 不得伪装成普通硬质行星

**视觉印象：** 云层形成巨大深度，浮空岛和高空平台悬浮在风暴层之间，远处有层叠的云墙与行星曲率。

**玩法：** 气囊平台、浮空采集站、风暴探针、气体采样和高度层航路。常规步行地表登陆不适用；必须走高空平台/气球探针/轨道无人机等专属玩法。

### 4.5.13 菌海深渊 `fungal_catacombs` — 一个有自己生态逻辑的地下世界

**视觉印象：** 巨型菌盖像穹顶，紫色孢子悬浮在洞穴空气里；菌丝沿石壁发光，地下湖反射青绿光。地表入口很少，进入后视线被一层层菌盖和岩层遮挡。

**玩法：** 洞穴探路、孢子过滤、共生培育、生物质回收、菌丝网络采样、地下水位控制。

### 4.5.14 机械圣骸 `ancient_megastructure` — 让行星历史体现在地形轮廓上

**视觉印象：** 地表像被远古文明加工过：巨型金属板块、断裂环带、垂直能量塔、巨大管道与腐蚀遗迹。机械结构不应全部对称，体现长久损坏和局部重力沉降。

**玩法：** 结构扫描、供能重启、AI 守卫、古代协议破解、模块拆解与技术遗产回收。建筑与自然岩层应在视觉上有明确区别。

### 4.5.15 硅晶风暴 `glassstorm_barrens` — 由风和磨蚀塑造的锋利地表

**视觉印象：** 沙丘像透明或半透明玻璃，低角度太阳形成锋利高光；远景有被风切削出的刀刃状山脊。风暴时沙砾像磨砂喷流一样横扫画面。

**玩法：** 抗磨蚀设备、硅晶收集、风暴掩体、精密光学设备维护、低能见度导航。地表行进方向和风向影响移动效率。

### 4.5.16 磁暴极光荒原 `magnetar_aurora` — 让天空也成为威胁系统

**视觉印象：** 深蓝黑地表上空出现大片紫青极光帘幕，磁暴时有波状脉冲和短暂放电。不要只是给天空贴一条极光贴图，要让天空的周期性变化与传感器、通讯和能源系统有关。

**玩法：** 电磁屏蔽、传感器遮蔽、临时通讯窗口、磁性矿采集、避雷设施、磁暴时限制外骨骼电子系统。

### 4.5.17 巨木云冠 `canopy_colossus` — 让垂直空间成为行星道路

**视觉印象：** 地表巨木像高耸建筑，树冠形成第二层地形；根系和藤蔓在空中连接，远处林冠像一片起伏的绿色云海。

**玩法：** 树冠桥梁、垂直攀爬、升降缆索、树脂/纤维材料、生态保护、空中掠食者巡逻。必须有地面层与树冠层两级地图高度。

### 4.5.18 碎环月 `fractured_moon` — 低重力和裂谷构成的遗迹打捞场

**视觉印象：** 灰褐色月面、巨大断裂峡谷、低重力悬浮碎石、轨道碎环在天空中形成独特背景。远景可看见母行星或碎环带。

**玩法：** 低重力跳跃、锚点/绳索、喷气背包、失事舱打捞、陨石坑采矿、真空环境生存。

## 4.6 主题混合和次级变体

混合主题只能增加世界差异，不得让主主题失去辨识度。例子：

- `abyssal_ocean + sulfur vents`：深海硫化喷口、化学能生态。
- `permafrost_furnace + ancient megastructure`：远古热能井成为唯一生存热源。
- `dry_night_polar + prism_crystal`：极夜盐晶地表叠加紫色折射晶柱。
- `red_regolith_frontier + glassstorm`：火星红色荒原与局部硅玻璃风暴区。
- `biolume_canopy + magnetar_aurora`：强磁暴触发夜间生态发光迁徙。

每个混合世界必须指定一个主主题，次主题只改变局部区域或特定环境事件。禁止把多个主题的所有效果同时叠加，造成色彩混乱和玩法失焦。

# 5. 登陆区域设计：人工设计的任务核心 + 确定性程序化外围

## 5.1 为什么不能全随机，也不能全手工

用户明确提出：登陆行星是为了做任务，落地点中心必须存在人工设计的小细节；往外走远后才进入随机地形。

这项要求必须成为正式关卡生成规则，而不是可选的美术增强。

全随机的缺点：任务关键结构不可控，路线可能不合理，目标可能埋入地形或出生在无意义空地。全手工的缺点：无法扩展到大量程序化行星，制作成本过高，长期探索缺乏变化。

因此采用：

**Authored Mission Core（人工任务核心） + Authored Transition Ring（人工控制的过渡带） + Procedural Frontier（确定性程序化外围）**。

## 5.2 三层空间结构

### A. 人工任务核心（Mission Core）

此区域围绕登陆点、任务目标和主要地标构建，必须是人工设计或数据驱动的手工蓝图。它不是随机摆件集合，而是具有空间叙事和行动路线的一个小关卡。

至少包含：

- 一处可辨认的登陆/集结区域（Landing Pad / Drop Zone）。
- 一个主视觉地标（例如热源塔、珊瑚穹顶、黑曜拱桥、远古天线阵列）。
- 两个以上辅助地标（残骸、设备、建筑、自然巨构、岩石群或信标）。
- 至少两条可行进路线，其中一条允许战术绕行/侧翼。
- 清楚的主要任务目标、次要目标和撤离目标。
- 至少一处可利用掩体或高低差。
- 至少一种主题机制（风暴、潮汐、温度区、腐蚀雾、磁暴、熔岩阻断等）。
- 初见时能读懂任务区域布局的视线/引导关系；关键目标不能全部藏在遮挡后。

### B. 人工控制的过渡带（Transition Ring）

此区域把任务核心自然过渡到程序化世界。应控制地貌坡度、地层材质、植被密度、岩石尺度和环境效果，让人工布置的基地不会像贴在随机地形上的模型。

过渡带可包含：
- 从整平任务区向自然地形恢复的高度渐变。
- 由人工道路向自然小径/岩脊的转化。
- 由受控照明向自然环境光的渐变。
- 从大量人工物件向稀疏自然 POI 过渡。
- 程序化装饰的密度逐步变化，不允许在半径边界出现突然的“人工/随机”断层。

### C. 程序化外围（Procedural Frontier）

外围地形由行星主题、seed、宏观地貌场和 biome 参数生成，提供非线性探索空间。可生成资源区、自然 POI、洞穴入口、异常环境、稀有生态和可采集点。

必须保证：
- 外围是同一颗星球的延伸，不是另一套拼接地图。
- 地貌与 Mission Core 的高度场和材质在边界连续。
- 外围 POI 有持久化 ID、状态和奖励锁。
- 任务关键目标不应仅靠随机散布；程序化外围可产生支线与发现，但主线可达性应来自明确目标图。
- 走得越远不应只是越来越空。应按探索距离/风险/扫描级别安排内容密度和危险强度。

## 5.3 推荐空间比例（可调参数，不作为绝对米制承诺）

以下是首期关卡构图比例，实际半径按当前地表尺度归一化：

| 区域 | 相对占地 | 内容密度 | 任务职责 |
|---|---:|---|---|
| Mission Core | 局部地图中心约 20–30% 的可视/可行走范围 | 高 | 主要任务、主地标、路线、交互和撤离 |
| Transition Ring | 紧邻核心的约 20–30% 范围 | 中 | 空间衔接、支线路线、局部危险和初级资源 |
| Procedural Frontier | 其余可探索范围 | 低到中，随距离/风险动态变化 | 自由勘探、稀有 POI、资源、环境挑战 |

不要把比例硬编码为世界坐标绝对长度。应采用 `siteRadius`、`coreRadiusFactor`、`transitionRadiusFactor` 等参数，以便地图尺寸、行星重力和任务人数变化时保持设计构图。

## 5.4 Mission Site Blueprint 数据契约

建议新增数据驱动的 `MissionSiteBlueprint`，由内容层提供模板，生成层把模板实例化到具体行星与 seed 上。示意：

```js
{
  id: "site_abyssal_ruin_01",
  version: 1,
  themeTags: ["abyssal_ocean", "ancient_megastructure"],
  siteKind: "underwater_ruin_survey",
  coreRadiusFactor: 0.28,
  transitionRadiusFactor: 0.25,
  terrainProfile: "submerged_shelf_with_trench",
  anchors: {
    landing: "anchor_dropzone",
    primaryObjective: "anchor_dome_gate",
    secondaryObjective: "anchor_power_spire",
    extraction: "anchor_submersible_bay"
  },
  landmarks: [
    { prefabId: "reef_dome_ruin", anchor: "anchor_dome_gate", rotation: 1.2 },
    { prefabId: "broken_tide_spire", anchor: "anchor_power_spire" }
  ],
  routes: [
    { id: "route_main", from: "anchor_dropzone", to: "anchor_dome_gate", kind: "wide_safe" },
    { id: "route_flank", from: "anchor_dropzone", to: "anchor_power_spire", kind: "narrow_risky" }
  ],
  objectiveGraph: "objective_graph_abyssal_survey_01",
  extraction: { kind: "submersible_bay", radius: 5 },
  proceduralSeedSalt: "abyssal_ruin_site_v1"
}
```

执行时按以下原则：

- 关键 Anchor 的存在和相对拓扑是确定的。
- 细节摆放可依 seed 做有限变化（石块偏移、碎片分布、照明损坏状态、装饰件旋转等）。
- 主要通路、任务目标、撤离点和任务必需道具不能被随机破坏。
- 同一世界 seed + 同一 blueprint version + 同一 generator version 应产生同一任务区域。
- 更换 blueprint version 应可区分为新内容版本，旧存档继续引用原 blueprint/version 或明确迁移。

## 5.5 关卡设计规则

每个正式登陆任务必须先回答：

1. 为什么玩家被派来这里？
2. 登陆后第一眼看到什么？
3. 玩家应该朝哪里走？
4. 主目标在哪里？它为什么在那里？
5. 有哪些路线选择？每条路线的风险/收益是什么？
6. 主题环境如何改变行动？
7. 任务失败或撤离时，玩家失去什么？
8. 任务完成后，世界会发生什么变化？

**首屏构图必须有明确焦点。** 不允许让玩家一着陆就面对没有地标、没有目标线索、没有方向提示的均匀随机山地。

### 5.5.1 任务区可读性

- 主要地标需要具有轮廓差异，不能只靠颜色分辨。
- 主要目标必须通过视觉地标、HUD 罗盘或任务轨迹至少一种方式可定位。
- 目标可以隐藏，但隐藏必须由扫描/调查机制解释，不能无提示地藏在噪点地形中。
- 撤离点必须在任务开始时就存在，并在玩家进入核心区后可被理解；不应在结尾才随机生成。
- 每个任务至少有一条基础可通行路线，不依赖玩家必须破坏地形才能继续。
- 至少一个可选路线应提供更快但更危险，或更慢但更安全的选择。

### 5.5.2 地貌与任务机制要互相证明

例如熔岩桥任务不应只是地上有一座黑色拱桥；桥必须真的跨越熔岩隔断，并改变路线和视野。冰封任务的裂谷必须迫使玩家修桥、绕行或寻找冰洞。硫雾任务的低地毒雾必须影响防护/视线，而高处风向站或抽气塔可成为任务目标。

# 6. 行星 GamePlay：从一次性登陆任务升级为可持续的探索—行动—经营循环

## 6.1 四类地表活动

行星地表不应只有“进入简报 → 选一个战斗任务 → 打完退出”。必须形成四类可互相连接的活动：

| 活动 | 目标 | 时间尺度 | 主要结果 |
|---|---|---|---|
| 先遣勘探（Survey） | 认识地貌、环境和 POI | 短至中 | 解锁行星信息、资源线索、遗迹入口、风险地图 |
| 战术行动（Mission） | 完成救援、调查、破坏、护送、防守或 Boss 目标 | 中 | 奖励、人员、设施状态、事件结果 |
| 自由地表作业（Field Work） | 采样、采矿、维修、地形处理、架设设备 | 中至长 | 原料、样本、设施、地形变化、任务准备 |
| 殖民/工业运营（Colony & Industry） | 建设基地、生产、物流、人口岗位、环境维持 | 长 | 持续资源流、制造链、前沿据点和战略影响 |

所有模式可以复用同一张地形、同一套 POI 和同一套存档；模式差别在于任务规则与可执行命令，不应建立互不相干的独立地图。

## 6.2 核心闭环

```text
从轨道扫描星球
    ↓
获得主题、环境、矿藏和异常的分层情报
    ↓
选择一个登陆点 / 任务场景
    ↓
进入人工设计的 Mission Core
    ↓
先遣队探索、调查、救援、采样或清除威胁
    ↓
进入外围探索，寻找持久化 POI 和额外资源
    ↓
把样本、情报、人员、资源和风险回写 World
    ↓
决定是否建立前哨/殖民地/采矿设施
    ↓
建设、生产、物流、科研和事件继续展开
    ↓
再次登陆执行后续任务或长期维护
```

## 6.3 轨道扫描与登陆准备

登陆前应至少显示：

- 行星主题和主环境标签。
- 重力、大气、温度、辐射、压力、液态/固态流体概况。
- 可探测矿产与置信度，不得把未调查的精确矿量当作已知事实。
- 已知 POI 数量/信号类别/定位误差。
- 预计登陆风险、装备建议、运输/补给成本。
- 可用着陆点及其地形风险：坡度、风速、表面稳定性、海拔、流体/熔岩/毒雾风险。

玩家选择登陆点时，系统应该显示着陆动画/镜头过渡，但不得为了视觉效果卸载和破坏可恢复的 World 状态。

## 6.4 第三人称角色与小队

保留当前项目已规划的第三人称外骨骼操控与战术小队，但操作必须以连续三角地形为基础：

- WASD/方向键移动，鼠标控制视角，跳跃/喷气/闪避/格挡/攻击按键可自定义。
- 相机使用 Spring Arm，遇到山体、建筑、桥梁或洞穴壁时自动收臂；不能穿地或长期卡在近裁剪面。
- 角色脚底贴合三角网格；移动时按地表法线和坡度调整姿态，避免身体漂浮或半埋。
- 角色碰撞应使用 Capsule/凸体与三角网格/高度场碰撞，禁止将视觉连续坡面重新离散为大方块碰撞。
- 小队 AI 必须能沿 NavMesh/坡度代价图/局部寻路导航，能使用掩体、过桥、绕开危险区。
- 高低差必须真实影响视线、射线、弹道和交互范围。
- 地表 UI 必须提供快捷工具栏：武器、扫描仪、采样器、维修器、地形工具、建造工具、小队指令等。

## 6.5 地形改造：从“挖方块”变成“雕刻地表与工程作业”

玩家可以改变地形，但主要交互方式不再是挖掉一个立方体或在相邻网格放置一个方块。

建议工具组：

| 工具 | 作用 | 可见反馈 | 规则约束 |
|---|---|---|---|
| 地形整形器 | 平滑、抬高、降低、压平小范围地形 | 连续地表逐渐变形，出现尘土/碎屑 | 消耗能量/材料；任务区或关键地标可锁定 |
| 地质钻探器 | 获取地下岩层与矿物样本 | 钻孔、岩芯、材质变化 | 受深度、硬度、温度和装备限制 |
| 采矿平台 | 对资源节点/矿脉开采 | 采掘机械、运输箱、资源量变化 | 按矿量和吞吐量结算，不能凭空产出 |
| 地面扫描仪 | 测绘坡度、地下密度、POI、环境污染 | 扫描脉冲、地图图层更新 | 信息逐级解锁，保留置信度 |
| 建造工具 | 放置模块化建筑、道路、桥梁、管线和地基 | 幽灵预览、地形贴合、施工动画 | 校验坡度、地基、材料、路径和环境适应性 |
| 修复/拆除工具 | 修复古代设施、拆除残骸或回收材料 | 结构渐进恢复/解体 | 资源、奖励和对象状态幂等 |

地形形变必须有预算。禁止每帧对整张地形重建；只重建被影响的 chunk 和必要邻接 chunk。地形改造存档保存可压缩差异或编辑命令序列，并能确定性重放。

## 6.6 POI、遗迹与任务实体

序列 5 已规定持久化 POI 和 WorldObjective，本文件进一步要求 POI 必须与地形主题、主视觉地标和任务核心相互呼应。

POI 的最小数据结构：

```js
{
  id: "poi_planet_xxx_001",
  planetId: "planet_xxx",
  themeId: "obsidian_lava",
  kind: "geothermal_vent_ruin",
  siteId: "site_lava_bridge_01",
  position: { x: 12.4, y: 8.2, z: -4.7 },
  discoveryState: "hidden", // hidden | detected | localized | discovered | exhausted
  interactionState: "available",
  threatLevel: 3,
  seed: 123456,
  rewardPaid: false,
  revision: 1
}
```

POI 类型应与主题相关：海底穹顶、冰层热泉、沙漠钻井、极夜晶体、硫磺喷口、发光生态巢穴、黑曜矿脉、棱镜晶簇、古代机械节点、玻璃风暴传感器、磁暴观测阵列等。

POI 完成后必须改变状态并可被再次访问；允许重复访问、持续产出或升级的 POI 必须有明确的冷却/产能模型，不能通过刷新地形重新生成奖励。

## 6.7 任务种类和任务设计密度

首期至少实现 8 种任务模板的高质量垂直切片，不要求一次性堆出数十个缺乏差异的任务：

1. 遗迹勘探与解密。
2. 科考队/失联人员救援。
3. 设施修复与重新供能。
4. 运输/护送与安全通道建立。
5. 采矿设备部署与资源样本回收。
6. 环境危害采样/控制（风暴、毒雾、潮汐、熔岩等）。
7. 敌对设施破坏/据点清除。
8. 生态调查/保护/隔离或危险生物清除。
9. 特殊主题 Boss 或大型异常事件（可作为后续扩展）。

每个任务必须包含：清楚的任务缘由、目标列表、空间定位、路线信息、风险、可用工具、撤离条件、奖励、失败结果和跨系统回写。

## 6.8 殖民地与工业设施必须尊重地形

建筑不再像小方块一样任意放在每个网格点。建议地基和模块化设施采用以下放置规则：

- 建筑底面投影到三角网格，计算高度差和坡度；超过阈值时拒绝、要求整地或使用桩基/支撑柱。
- 大型建筑必须有占地 footprint、地基边界、入口/道路连接和维护空间。
- 输送带、管线、道路、栈桥和电缆用 spline/polyline 生成连续几何，拐弯、坡度和高差必须可视化。
- 对熔岩、海洋、沼泽、冰面、浮岛等特殊地表，应使用主题专属基础设施（高架桥、浮台、耐腐蚀桩基、隔热地基等）。
- 建筑施工应表现为施工阶段：地基、主体、连接管线、启用；状态变化由领域模型驱动。
- 玩家拆除/整地时保留或恢复植被、岩石、地表装饰的策略应明确。DSP 近期更新展示了一个值得借鉴的方向：施工清除的岩石/植被可以回收后重新摆放，且支持将修改地形恢复到自然状态。该机制可启发 VOID FRONTIER 的“地表扰动可逆/生态恢复”系统。[^6]

## 6.9 行星主题必须进入经济、科技和外交

主题不是一次性美术内容；它必须决定该星球能提供什么、建设成本如何、有哪些独占科技或外交价值。

例子：

- 碧渊海洋：海水淡化、深海压力材料、潮汐能、海底生物材料、深潜器。
- 永冬炉境：隔热合金、热交换器、地热能源、耐寒设备、热网络。
- 赤砾边疆：铁族矿、硅酸盐、地下水、太阳能阵列、尘暴过滤设备。
- 硫雾沼泽：挥发性气体、硫化物、耐腐蚀涂层、过滤器、化工链。
- 星辉生物圈：生物质、共生纤维、药物前体、生态改造技术。
- 黑曜熔海：地热、耐高温材料、玄武岩纤维、热防护、熔岩桥梁工程。
- 磁暴极光荒原：磁性矿、超导材料、屏蔽技术、磁暴观测。

以上只是示例；每个主题至少要有 1 个“独有优势”、1 个“独有风险”和 1 个“对其他世界/系统有需求的产物”。否则主题价值仍然停留在表面。

# 7. 程序化生成：确定性、主题约束和人工设计协同

## 7.1 随机必须有结构

程序化生成不是把噪声叠加到所有东西上。必须先有语义结构，再用噪声填充结构内部的自然变化。

推荐生成顺序：

1. 读取 Planet Entity：类别、半径、重力、大气、温度、水、辐射、磁层、资源、轨道和恒星数据。
2. 选择主题 `themeId` 和次级 modifier；校验与天体物理参数兼容。
3. 选择宏观地貌 archetype：海盆/台地/裂谷/冰原/火山高地/巨构残骸等。
4. 生成区域分布：biome patches、危险区域、资源场、生态场、气候区。
5. 生成 landing site blueprint：根据主题、任务类型和任务条件挑选人工场景模板。
6. 把 blueprint 关键地标和道路约束融入地形高度场/三角网格。
7. 生成 transition ring 与 procedural frontier。
8. 在外围按规则生成 POI、采样点、矿区和次要地标。
9. 运行质量验证：坡度、路径、目标可达、视线、撤离点、场景边界和主题一致性。
10. 生成视觉资源缓存，但存档只保存规则状态/编辑差异与版本信息。

## 7.2 随机子流隔离

行星地貌、装饰、任务场景、POI、生态群落和粒子相位必须使用可复现子随机流。不能因为增加一棵树或一块石头，就改变同一个 seed 下的任务目标、奖励或世界经济状态。

建议使用：

```text
worldSeed
 ├─ galaxySeed
 ├─ systemSeed(systemId)
 └─ planetSeed(planetId)
     ├─ themeSeed
     ├─ macroTerrainSeed
     ├─ biomeSeed
     ├─ missionSiteSeed(siteId, blueprintVersion)
     ├─ poiSeed(poiId)
     ├─ decorationSeed(regionId)
     └─ cosmeticSeed
```

每个子流的 salt/算法/版本必须稳定；世界主 RNG 不能被地表装饰生成器消费。逻辑随机和纯视觉随机必须分离。

## 7.3 生成结果质量门禁

每张生成地表在进入游戏前或 debug test 中验证：

- 无 NaN/Infinity 顶点和矩阵。
- 无零面积三角形、重复索引或无效 index。
- 任务锚点均落在可走区域或有明确特殊通行方式。
- 角色出生点坡度/高度安全。
- 主路线连通，支线路径具有明确通行/风险属性。
- 撤离点可达，且不被随机地形封死。
- Mission Core 与 Transition Ring 边界高度/材质连续。
- POI 与地标不重叠、不埋地、不悬浮。
- 主题色、地貌和机制三者一致。
- 不同 seed 产生可感知变化，但不改变主题身份。

生成失败时必须使用有记录的回退模板或重新派生有限次数；不能静默生成一个空白平地并宣称成功。

## 7.4 稀疏不是空洞

外围程序化区域可以比任务核心更稀疏，但不能无内容。内容密度可按玩家离登陆点距离和探索进度分层：近外围放置可识别次级地标和资源；中外围放置稀有 POI、危险区和环境变化；远外围放置高风险、高价值或长线任务入口。

必须留出具有审美价值的空旷空间，但空旷需要有视线、轮廓、光照、天气和环境声支撑。**“没有对象”可以是一种构图选择；“没有设计”不能被解释成留白。**

# 8. 视觉表现与声音：让主题被玩家感知，而不只被数据库识别

## 8.1 三个观察距离

| 距离 | 必须读出的信息 | 主要视觉手段 |
|---|---|---|
| 轨道/远景 | 主主题、海陆/冰盖/熔岩/云带/巨构等地貌身份 | Planet shader、云层、极冠、反照率、夜侧灯光、主题大色块 |
| 地表中景 | 山脊、峡谷、海岸、任务地标、建筑区、危险区域 | Terrain mesh LOD、材质混合、地标网格、天气层、空间轮廓 |
| 角色近景 | 脚下地表、材质细节、交互物、采样/破坏效果、角色动作 | 高精度 Mesh、法线、贴花、粒子、工具动画、局部阴影 |

## 8.2 环境光照必须由主题和恒星共同决定

环境光照至少受以下输入影响：

- 主恒星类型与色温。
- 太阳高度和行星自转/日夜周期。
- 大气成分、密度、雾和散射色。
- 地表湿润度、矿物反照率、植被/晶体的自发光。
- 天气（沙暴、雪暴、硫雾、海雾、火山灰、磁暴等）。

不能固定太阳方向、固定雾色和固定天空渐变覆盖所有主题。需要可调的艺术参数和基于主题的物理近似。

## 8.3 透明/半透明层的渲染顺序

水体、毒雾、薄云、能量膜、透明晶体和玻璃结构必须有明确 pass 顺序、深度写入策略、排序方式和颜色混合规则。禁止把所有透明对象混在同一个无序数组里直接绘制。

水下场景至少实现：水路雾、RGB 波长吸收、深度阳光衰减、海床焦散、稀疏悬浮颗粒；这些效果应分别可开关，避免低性能设备上一次性全部启用。[^3][^4]

## 8.4 声音属于主题身份

建议为不同主题设计独特的环境声层：

- 碧渊：低频水压轰鸣、遥远鲸鸣式原创合成音、气泡、金属共振。
- 永冬：风洞低鸣、冰裂声、热源设备节律。
- 赤砾：干燥风声、砂砾撞击、远处矿业设备。
- 永夜晶荒：高空电离静噪、稀疏晶体敲击、地热低频。
- 硫雾：气体脉冲、泥浆气泡、腐蚀滴落声。
- 星辉生物圈：昆虫群/植物脉动的抽象合成声、夜间生态鸣响。
- 黑曜熔海：熔岩流动、岩石爆裂、热压喷发。
- 棱镜晶原：晶体共鸣和光学扫描音。

音频不得依赖外部音频资源或网络请求；遵守原任务书关于 Web Audio 与首次交互解锁的限制。环境声必须可关闭，不能影响规则。

# 9. 性能、静态部署与架构约束

## 9.1 必须继承的工程约束

本文档不允许以下做法：

- 新增运行时 CDN、远程 API、云端资产下载或必须依赖服务器端逻辑的玩法。
- 把渲染逻辑写入 domain/simulation，或让 Renderer 直接修改 World。
- 把 WebGL Buffer、DOM、Canvas、GL Handle、相机对象直接写入存档。
- 使用 `Math.random()` 影响世界生成或玩法结果。
- 将主世界 RNG 消费与装饰/地形生成耦合。
- 通过 UI 假数据冒充资源、任务、采矿、建筑或探索已完成。
- 为了实现地表而分裂成第二个独立小游戏、第二个 World Store 或独立存档。

## 9.2 推荐模块边界

目录名以当前仓库为准，以下仅定义职责，不能要求为了目录一致而机械搬迁：

```text
content/planetThemes.js          # 主题定义、调色板、兼容约束、POI/建筑/天气池
content/missionSites.js          # 人工任务场景蓝图
content/terrainProfiles.js       # 地貌 archetype 和生成参数

domain/ground/                   # 地形逻辑、POI、采掘、任务、环境机制
  terrainField.js                # 高度/地质/环境语义场
  terrainEdits.js                # 地形修改命令及持久化差异
  surfaceQueries.js              # 高度、法线、坡度、射线、碰撞
  planetPOI.js                   # POI 状态和幂等回写
  missionSiteFactory.js          # Blueprint 实例化与质量验证

render/gl/                       # 纯表现层
  PlanetTerrainMesh.js           # Chunk Mesh / LOD / 材质权重
  PlanetAtmosphere.js            # 大气、天空和天气
  PlanetWater.js                 # 水体/透明流体 pass
  PlanetSurfaceScene.js          # Terrain + Objects + Actors + Effects 编排

ui/screens/GroundView.js         # 输入、导航、HUD、模式切换；不拥有规则数据
ui/screens/ColonyView.js         # 殖民/工业管理视图
```

地形逻辑在 CPU/domain 层生成确定性数据；Render 层根据只读快照或专门的只读地形投影构建 GPU Mesh。玩家动作通过命令或明确定义的短周期控制输入修改领域状态，不得由 Render 层直接扣资源或发放奖励。

## 9.3 性能预算与降级策略

建议目标（需在实际浏览器和设备上测量，不作为未经测量的硬承诺）：

- 普通桌面设备常规地表运行目标 60 FPS；低配设备允许 30 FPS 目标。
- 近景 Mesh 保持足够地貌轮廓质量，远景必须通过 LOD 降低三角密度。
- 对地形按 chunk 做视锥剔除、LOD、缓存和增量重建。
- 不因角色每移动一小步就重新生成整张地表网格。
- 粒子、植被实例、岩石和建筑采用实例化/对象池/批处理。
- 水面透明层、体积雾、反射和 Bloom 必须分级关闭或降采样。
- WebGL context lost 时保留可解释的基础视图/降级提示；不能让 World 或存档损坏。
- 低端模式可以减少装饰密度、阴影、反射和远景细节，但不能改变资源、地形碰撞或任务规则。

不要为了追求几何细节无限加密。三角形预算应以屏幕空间误差、地貌复杂度和设备实测为依据。NVIDIA Geometry Clipmaps 的技术价值在于保持屏幕空间三角大小相对均衡、局部更新、过渡平滑，而不是某个固定三角数。[^2]

## 10.3 保存哪些数据

必须保存：

- `primaryThemeId`、主题/生成器版本。
- planet seed、site blueprint ID/version、mission site instance seed。
- 已发现/已耗尽/已完成 POI 状态、奖励幂等标记。
- 已完成的地形编辑、建筑、道路、桥梁、设施和采掘记录。
- 资源节点剩余量、环境设施状态、任务和人物状态。
- 玩家选择的登陆点和可以恢复的任务进度。

通常不必保存：

- 每帧渲染矩阵、相机 shader uniform、GL Buffer、LOD 临时网格、粒子瞬态视觉缓存。
- 可由 seed 和 generator version 完全重建的装饰顶点。

## 10.4 版本迁移

旧存档目前可能含有 `surfaceWorld.voxels`、`heights`、`chunks`、`stats` 等体素字段。迁移时必须：

1. 识别旧存档 schemaVersion 和地形 generator version。
2. 保留旧 planet seed、已采矿量、任务记录、POI 状态和已建造设施。
3. 将已采掘体素归纳为资源消耗记录/资源节点余量差异；将已放置 BUILDING 体素迁移为对应结构或明确的兼容占位实体。
4. 新地形按同一 planet ID 和固定迁移版本重新生成；不得在加载时偷偷抽一个新随机主题。
5. 不能精确映射的旧地形编辑必须放入兼容日志并给出迁移策略，不能直接静默丢弃。
6. 迁移后通过资源账本、任务奖励、POI 幂等和实体引用完整性测试。

# 11. 分阶段施工路线与执行顺序

执行工程师必须以“先可验证，再扩内容”为原则。每个阶段先写测试和失败判据，再实现，最后通过浏览器完成实际验收。

## Phase 0 — P0 渲染故障止血

**目标：** 修复当前地表背景残影与地形缺失，使旧地表至少可以稳定显示，为 Mesh 重构建立可信基线。

- 显式 clear color/depth；明确 FBO/viewport/scissor/colorMask。
- 地形绕序、法线、背面剔除和相机高度诊断。
- 建立 Terrain Debug View：wireframe、normal、material ID、chunk bounds、LOD、坡度、碰撞。
- 添加 GL state snapshot 和 error log。
- 修复 HUD/GL 画布之间的清除和透明混合边界。

**门禁：** 通过第 3.4 节所有验收；不得以“开发者电脑上看起来好了”替代截图、GL 状态和回归记录。

## Phase 1 — 三角网格地形垂直切片（P0/P1）

**目标：** 在一颗测试行星上实现完整的非方块、连续三角地形，从生成到渲染、碰撞和角色移动形成闭环。

范围：
- 新建 heightfield/terrain field 和三角网格生成。
- 实现 material weights、顶点法线、坡度/高度语义。
- 实现网格射线拾取和角色落地碰撞。
- 将一个旧 Mission Core 映射至三角网格，保持任务规则可运行。
- 旧体素地图暂时保留为兼容数据，不再作为主要视觉。

**门禁：** 一颗岩质/火星主题行星能看到连续山脊、盆地、坡面和道路；角色能正常行走、跑跳、射击和互动；旧任务结算幂等不被破坏。

## Phase 2 — 人工任务核心 + 程序化外围（P1）

**目标：** 先实现一个主题、一套人工关卡和多个外围程序化区域。

首个垂直切片推荐：`red_regolith_frontier` 或 `obsidian_lava`。两者都能用强烈轮廓、清楚危险区和显著人工结构验证地形设计。若团队更重视水下氛围和透明渲染，可选 `abyssal_ocean`，但需把水体 pass 作为独立高风险工作。

交付：
- `MissionSiteBlueprint`。
- Mission Core、Transition Ring、Procedural Frontier。
- 两条路线、一个主目标、一个次要目标、一个撤离点、一个主题环境机制。
- 3 个以上持久化 POI。
- 同 seed 重建一致，不同 seed 装饰/局部细节有变化。

## Phase 3 — 主题系统与主题首批 6 个（P1）

必须完成：
1. 碧渊海洋。
2. 永冬炉境。
3. 赤砾边疆。
4. 永夜晶荒。
5. 硫雾沼泽。
6. 星辉生物圈。

这六个主题覆盖水、冰、干燥荒原、永夜、腐蚀气体与生态世界，能验证主题系统不是简单 Tint。每个主题必须至少具备主地貌、天空/光照、两种 POI、一个标志性地标、一种危险机制、一条资源链或科技钩子。

## Phase 4 — 高辨识度主题扩充（P2）

加入：黑曜熔海、棱镜晶原、镜盐荒原、甲烷雾海、晨昏环带、云海浮岛、菌海深渊、机械圣骸、硅晶风暴、磁暴极光荒原、巨木云冠、碎环月。

气态巨行星必须采用专属浮空/探针玩法，不能默认地表登陆。

## Phase 5 — 行星工业/生态/地形改造深化（P2/P3）

- 建筑与坡度/地基/桥梁系统。
- 道路、管线、传送带 spline 和物流实体。
- 地形平滑/抬升/压低/恢复。
- 生态/矿物/资源节点持久化。
- 环境修复、植物/岩石回收再部署。
- 殖民者岗位/工作任务/维修/采集作业。
- 多主题长期世界存档和跨行星物流。

# 12. 验收矩阵：不能只验收“能生成”和“能渲染”

## 12.1 地形几何与渲染

| ID | 场景 | 通过标准 |
|---|---|---|
| TERRAIN-01 | 三角网格生成 | 无 NaN/Infinity、无零面积三角、无非法索引 |
| TERRAIN-02 | 三角绕序 | 已知朝外面法线和三角 winding 一致，Cull 正式模式下无地表消失 |
| TERRAIN-03 | 法线 | 斜坡光照连续；硬边和软边按材质 profile 正确区分 |
| TERRAIN-04 | 地形 LOD | 视角移动时无裂缝、明显 Pop 和悬浮边 |
| TERRAIN-05 | 地形碰撞 | 角色脚底贴合三角面，不能穿透或漂浮 |
| TERRAIN-06 | 地表修改 | 修改局部后只更新受影响 chunk，邻接边界正确 |
| TERRAIN-07 | 背景清除 | 每帧 color/depth 清理稳定；长时间拖动无残影 |
| TERRAIN-08 | GL 状态恢复 | context lost/restored 后 renderer 正常重建 |
| TERRAIN-09 | 三角密度 | 近景细、远景粗；画面质量和性能符合目标预算 |

## 12.2 主题辨识和一致性

| ID | 场景 | 通过标准 |
|---|---|---|
| THEME-01 | 轨道远景 | 缩略图/轨道上能识别主主题轮廓，不依赖 UI 文本 |
| THEME-02 | 地表中景 | 地貌轮廓、主材质、天空和天气符合主题 |
| THEME-03 | 地表近景 | 材质细节和交互对象可辨认，不形成平铺噪点 |
| THEME-04 | 主题玩法 | 主题至少改变一种移动/环境/采集/建筑/任务规则 |
| THEME-05 | 资源闭环 | 主题独特资源进入账本、制造或科研，不是纯展示 |
| THEME-06 | 主题混合 | 次级 modifier 不覆盖主主题身份，不产生色彩混乱 |
| THEME-07 | 不同 seed | 同主题保持核心身份，局部形态和装饰有合理变化 |

## 12.3 任务区与程序化外围

| ID | 场景 | 通过标准 |
|---|---|---|
| SITE-01 | 人工 Mission Core | 有 landing zone、主地标、主目标、撤离点和路线 |
| SITE-02 | 双路线 | 至少两条可行路线，风险/时间/视野有差异 |
| SITE-03 | 任务可达性 | 主线目标与撤离点可达，随机装饰不能堵死路径 |
| SITE-04 | 过渡带 | 人工区域与外围地貌无突变拼缝 |
| SITE-05 | 程序化外围 | 能生成多样地形、次要地标和持久化 POI |
| SITE-06 | Seed 确定性 | 相同 seed+blueprint version 结果一致 |
| SITE-07 | 编辑持久化 | 地形修改、建筑、道路和已完成 POI 能存档恢复 |
| SITE-08 | 首屏引导 | 玩家着陆后能看懂当前目标和首条建议路径 |

## 12.4 Gameplay 闭环

| ID | 场景 | 通过标准 |
|---|---|---|
| GAME-01 | 轨道扫描 | 主题、环境、资源和 POI 情报逐级揭示 |
| GAME-02 | 未殖民登陆 | 无殖民地仍能进入先遣勘探模式 |
| GAME-03 | 采样 | 样本在任务完成后正确进入 World/库存 |
| GAME-04 | POI 幂等 | 重复交互/重新进入/读档均不重复发奖 |
| GAME-05 | 环境危险 | 主题环境实际影响防护/移动/视野/耗材等至少一项 |
| GAME-06 | 地形工具 | 平滑地形改造实际影响通行/建造/任务路线 |
| GAME-07 | 建筑落位 | 建筑地基贴合地面，坡度过大时阻止或需要工程处理 |
| GAME-08 | 物流 | 管线/道路/运输路径连通，吞吐量与账本一致 |
| GAME-09 | 任务回写 | 成功、失败和撤离结果回写主世界且幂等 |
| GAME-10 | 返回导航 | 任何地表模式能返回所属行星/星系，不产生软锁 |

## 12.5 稳定性、存档与部署

- 固定种子生成 100 张以上的主题地表，所有质量门禁通过。
- 多个任务蓝图和主题组合都能正常进入与退出。
- 连续加载/卸载地表场景 100 次，不发生 GL 资源泄漏、旧画布残留或 RAF 循环残留。
- 保存后刷新页面，地表主题、POI、资源、任务进度和玩家编辑能够恢复。
- 同一个存档在旧版迁移到新版后，资源账本和任务奖励无重复/丢失。
- 纯静态 HTTP 和 GitHub Pages 二级路径都能运行；无运行时外部网络请求。
- 全量测试必须包含领域测试、渲染状态单测/集成测试、浏览器 UI E2E 和固定种子截图/几何快照。

# 13. 自主执行 Agent 的施工纪律

执行工程师必须把本文档当作真实产品规格，而不是灵感建议。遇到规格未覆盖的细节时，允许自主决策，但必须记录理由、影响范围和验证方式。

## 13.1 开工前固定动作

1. 检查当前工作树、分支、HEAD、未提交修改和最近提交。
2. 阅读本文档、序列 1–5 的相关章节，以及当前地表代码。
3. 记录旧实现与目标实现的差异清单，不得先删文件再分析依赖。
4. 建立当前渲染故障复现用固定存档/固定主题/固定相机操作路径。
5. 先新增诊断测试/日志，再修复渲染 bug。
6. 为 Mesh Terrain 画出数据流：Planet Entity → TerrainField → Mesh Builder → Collision/Navigation → Renderer。
7. 为 Mission Core 定义 blueprint 和验收布局草图/数据，不得只凭噪声生成关卡。

## 13.2 执行顺序

严格遵守：

`P0 Render Stability → P1 Triangulated Terrain Vertical Slice → P1 Authored Mission Site → P1 Theme System (6 themes) → P2 Theme Expansion → P2/P3 Industry & Ecological Depth`。

不得在当前地表仍然背面消失、残影和无法稳定操作时，就开始堆大量主题美术。

## 13.3 不得做的事情

- 不得用几张概念图/一张静态背景冒充可玩地形。
- 不得将地形简化成大量规则方块。
- 不得仅更换颜色变量就宣称新增主题。
- 不得让所有 POI 都随机散布，任务主线仍需人工设计。
- 不得生成没有作用的装饰资源/资源数值。
- 不得为了短期效果删掉旧存档、旧任务数据或世界状态。
- 不得让 Renderer 修改资源库存、发放奖励或改变 World 规则。
- 不得以“页面不报错”“WebGL draw call 成功”代替玩家体验验收。

10. 当前 Git commit 和下一步最小任务。

# 14. 最终体验验收：Playable Planet，不是 Planet Screenshot

当且仅当以下体验全部成立，才允许将“行星主题与地表系统”标记为 `verified`：

- 玩家从银河/星系层看到一颗星球时，可以从其外观辨识主主题。
- 玩家查看行星详情时，能理解该主题意味着什么环境、风险、资源和行动机会。
- 玩家选择登陆点时，知道为什么在这里登陆、要完成什么任务、预计会遇到什么风险。
- 落地后看到的是连续三角网格自然地形，而不是 Minecraft 方块地面。
- 登陆点附近是人工设计的任务核心：有地标、有路线、有目标、有掩体、有撤离区、有主题机制。
- 向外探索时，地貌自然过渡为程序化地形；不会突然出现地图边界、拼接断层或无穷空白。
- 每个主题不仅颜色不同，而且至少在地貌、天气、危险、工具或资源中有明显差异。
- 玩家能执行调查、采样、救援、修复、采矿、战斗、建造或环境处理中的多种活动。
- 任务/POI/地形变化会影响 World、资源、科技、殖民和事件，而不是只在本画面内播放动画。
- 重新进入同一行星时，已完成的 POI、采掘结果、建筑和地形修改仍然存在。
- 玩家能随时返回轨道/星系，不能因为简报、模式或旧 Inspector 遗留而软锁。
- 相同 seed 和版本能复现相同逻辑地形、任务目标和奖励；装饰差异也具有明确的 seed 来源。
- 场景运行稳定：没有背面剔除造成的地表缺失，没有残影，没有 LOD 裂缝，没有穿地和悬浮。

**最终验收不是“我生成了一颗好看的星球”，而是“玩家在这颗星球上有理由登陆、有地方可去、有事情可做、有路径可选、有结果可带回，并且下次回来时世界记得他做过什么”。**

   高度场通过 Delaunay 三角化近似，使用最大误差阈值控制顶点/三角形数量。可参考其误差约束思路，不能直接将其作为生产环境远程依赖。
