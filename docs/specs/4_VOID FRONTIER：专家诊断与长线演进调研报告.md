一、执行摘要：项目已经有较强的引擎底座，但尚未完成从“可运行”到“好玩、好操作”的跨越
我对项目的总体判断是：

VOID FRONTIER 已经建立了一个相当有价值的确定性 4X 模拟内核和程序化三维表现底座，但当前最大的短板不是渲染能力、模拟精度或者代码规模，而是游戏世界、交互状态、任务目标和可操作内容之间尚未形成足够完整的连接。

这一区别非常重要。

现在的项目已经具备：
- 40,000 恒星粒子级的银河表现。
- 基于确定性随机数的星系和行星生成。
- 统一 World 状态、CommandBus、EventBus 和分级 Tick Pipeline。
- 舰队、经济、科研、外交、战斗、殖民和人物系统。
- 具有实际地形、矿脉和体素网格的行星地表系统。
- 本地持久化、存档迁移、确定性回归和 GitHub Pages 发布能力。
这些并不是简单的网页演示功能，而是具有一定系统深度的游戏工程基础。

但是，你目前报告的问题显示出了明显的另一面：
- 玩家能够看到行星，却不能自然地进入下一个交互层级。
- 玩家能够看到事件，却不知道应该到哪里采取行动。
- 玩家能够看到地表，却可能没有实际可执行的探索活动。
- 玩家能够看到复杂的情报面板，却不能稳定地保持自己刚刚做出的 UI 操作。
- 游戏存在多个层级的视图，却没有形成可靠的统一导航和生命周期管理契约。
这意味着项目存在一个核心矛盾：
底层模拟已经可以描述一个复杂的星际文明，但玩家还没有足够自然、连续、可预测的方式去观察、理解和干预这个文明。

我建议暂时不要把项目定义成一个需要继续增加大量星球、文明、建筑和武器的内容扩张阶段。

它当前更需要一次：

交互系统收敛 + 空间任务系统补全 + 前殖民期探索机制建立。

这三项工作将直接决定项目从技术验证级沙盒迈向长期可玩产品的速度。

3.1 问题一：星系视图无法通过行星直接进入下一层级
P0：核心交互缺陷
当前 SystemView._bindCanvasEvents() 的主要事件包括：
mousedown
mousemove
mouseup
click
wheel
mouseleave


没有 dblclick 处理。

当前单击行星的行为主要是：
const hit = this._renderer.pick(p.x, p.y);

this._selectedPlanetId = hit || null;
this._highlightPlanetCard(hit);

if (hit) {
  this.app.select('planet', hit);
}


它完成的是：
- 行星拾取。
- 当前行星选择。
- 右侧情报联动。
- 行星卡片高亮。
并没有在 Canvas 的空间交互中执行 前往 或进入行星下一层级的路由动作。

这里需要纠正一个细节：星系情报舱并非完全没有行动入口，行星卡片在满足条件后存在建立前哨、登陆等操作按钮。因此并不是所有情况下都无法继续游戏，而是空间对象的直接操作与情报面板中的行动按钮没有统一起来。

我的建议是采用以下操作语义：
输入	建议行为	目的
单击行星	选中行星	保持现有行为
双击行星	聚焦并进入行星详情	提供直接空间导航
回车 / Space	对当前选中行星执行默认进入动作	键盘可访问
右键	打开上下文行动菜单	快速操作
卡片按钮	登陆、建立前哨、扫描等	明确执行具体行动

这里有一个重要设计判断：

双击不应一律等同于“立刻登陆地表”。

建议把层级做成：
银河
  ↓ 双击星系
星系
  ↓ 双击行星
行星详情
  ↓ 点击登陆
行星地表


双击是一种空间层级推进操作，登陆则是一个明确的游戏行为。

这样既符合玩家直觉，也不会因为误双击导致突然切换场景。

从现有星系 Canvas 的拾取机制出发，增加这一套操作不需要重写渲染引擎。

3.2 问题二：行星光辉与行星主体发生约 2 倍距离的错位
P0：确定的图形数学错误
这个问题已经可以从代码和矩阵运算中直接证明。

当前 GLOW_VERT 的核心逻辑：
vec4 w = uModel * vec4(aPos * uRadius, 1.0);

vWorld = w.xyz;
vN = mat3(uModel) * aPos;

gl_Position = uMVP * w;


而 CPU 端构建的 MVP 是：
mat4Multiply(s.vm, s.view, s.model);
mat4Multiply(s.vp, s.proj, s.vm);


也就是说：
\[
MVP=P\times V\times M
\]

着色器又先执行：
\[
w=M\times p
\]

最后：
\[
glPosition=(P\times V\times M)\times(M\times p)
\]

等于：
\[
P\times V\times M^2\times p
\]

由于当前 Model 矩阵中包含行星中心的平移向量，平移被重复应用。

设行星中心为：
\[
C=(x,y,z)
\]

那么本来应该得到：
\[
C
\]

实际却得到了：
\[
2C
\]

这与你观察到的“光辉壳体仿佛被移动到了轨道半径的两倍位置”完全吻合。
修正建议
不必改变现有渲染管线，只需统一变换契约。

可以采用以下写法：
void main() {
    vec4 localPos = vec4(aPos * uRadius, 1.0);
    vec4 worldPos = uModel * localPos;

    vWorld = worldPos.xyz;
    vN = normalize(mat3(uModel) * aPos);

    // uMVP 已经是 P * V * M，因此直接使用局部坐标
    gl_Position = uMVP * localPos;
}


这里的关键是：
- worldPos 用于世界坐标和光照计算。
- uMVP 用于直接变换局部坐标。
- Model 变换只应用一次。
另一种写法是让 CPU 提供 uVP=P×V，着色器使用：
gl_Position = uVP * worldPos;


两种方案都可以成立，但必须选择一种统一的矩阵契约。

另外，建议把类似问题写进渲染器测试规范：
1. 星球本体与大气壳体使用同一个世界中心。
2. 轨道编号为 0、1、3、7 的多个行星都要验证。
3. 测试 2D 与 WebGL2 两条渲染路径。
4. 如果后续加入非均匀缩放，法线矩阵应采用逆转置矩阵，而不是简单的 mat3(uModel)。
这项修改属于明确的数学修复，不应该演变成一次大规模图形重构。

3.3 问题三：左侧导航栏遮挡非地图视图
P0：全局布局架构缺陷
当前 .vf-sidebar 采用：
position: fixed;
left: 10px;
width: 46px;
z-index: 40;


悬停后：
.vf-sidebar:hover {
  width: 176px;
}


这是一个悬浮式导航栏，而非真正参与页面布局的导航栏。

问题在于，很多视图的 .vf-view-body 并没有统一的左侧安全区域约束。

因此，视图容器并不知道左边存在一个宽度可能从 46px 变化到 176px 的导航控件。

这会造成两种结果：
- 页面内容默认从视口左侧开始排布，部分内容被导航栏覆盖。
- 各个页面分别尝试用 padding 或 margin 修补，最终形成不一致的布局行为。
这里不能简单地给所有页面增加：
margin-left: 60px;


因为银河界面和星系界面本来就需要保留沉浸式的完整画布。
正确方案：全局布局模式
建议定义两种布局：
模式	适用界面	行为
immersive	银河地图、星系轨道、特定战斗视图	画布全屏，导航悬浮在安全区域
management	殖民地、科研、外交、市场、政策、舰船管理	页面主动为导航栏预留空间

结构示意：
Application Shell
│
├── Sidebar
│
├── Main Workspace
│   ├── View Header
│   ├── View Content
│   └── Optional Inspector
│
└── Global Notification / Status Layer


管理界面采用 CSS Grid 或 Flexbox 预留真实布局宽度。

沉浸式界面依旧全屏，但所有按钮和面板都必须具有明确的安全边距。

还需要明确一个细节：导航栏展开时究竟是覆盖内容，还是推动主内容区域移动。我的建议是：
- 管理界面：展开时采用布局推移，必要时使用平滑动画。
- 沉浸式界面：导航栏仍然覆盖，但地图对象、可点击控件和关键文字不得被遮挡。
产品任务书本身已经要求左侧导航、中央工作区和右侧检视器形成统一指挥台布局，同时支持沉浸式地图和管理型面板。当前问题实际上是这一设计原则没有被系统性落实。

3.4 问题四：星系右侧 Collapse 展开后立即缩回
P0：UI 瞬态状态管理缺陷
这是一个典型的 Vanilla JS 项目容易遇到的问题。

当前 SystemView.onSnapshot() 采用大约 250ms 的节流：
onSnapshot(snap) {
  if (!this._mounted) return;

  const now = performance.now();

  if (now - this._lastRefresh < 250) return;

  this._lastRefresh = now;
  this._refreshAll();
}


而 _refreshAll() 会重新构建右侧情报舱：
_buildDossier() {
  const box = this._dossier;
  if (!box) return;

  clearEl(box);
  this._planetCards = new Map();

  // 重新创建全部面板
}


折叠组件是通过 panel() 生成的 DOM 结构。

点击展开时，改变的是当前 DOM 实例的瞬态状态。

然而，下一次快照到来时：
1. 旧 DOM 被整体销毁。
2. 折叠组件失去原来的展开状态。
3. 新 DOM 被创建。
4. 新面板重新采用默认状态。
这不是折叠组件本身的错误，而是快照更新与 UI 瞬态状态没有解耦。
不推荐的解决方法
不要仅仅把刷新间隔从 250ms 改成 1 秒。

这只是延迟问题发生，不是解决问题。

也不要把整个快照刷新关闭，否则舰队状态、调查进度、异常信息等内容可能变得陈旧。
推荐方案：UI 状态独立化 + 局部差异更新
建议建立一个轻量的 UI State Store：
uiState = {
  systemView: {
    panels: {
      dossier: true,
      planets: true,
      fleets: false,
      anomalies: true
    },

    selectedPlanetId: null,
    scrollPosition: 0,
    focusedControlId: null
  }
};


面板状态使用稳定 ID 保存，而不是依赖 DOM 是否存在。

同时将刷新逻辑拆成：
Snapshot Update
    ↓
Compare Previous / Current View Data
    ↓
Update Changed Fields
    ↓
Preserve DOM Identity
    ↓
Preserve User Interaction State


在没有前端框架的情况下，并不需要引入完整的 Virtual DOM。

只需要：
- 保留静态 DOM 结构。
- 对有稳定 ID 的节点进行局部更新。
- 对复杂子列表做 keyed reconciliation。
- 对交互状态单独存储。
建议把以下状态全部纳入保护范围：
UI 状态	是否应在快照更新时保留
Collapse 展开/闭合	是
当前选中的行星	是
情报舱滚动位置	是
输入框内容和焦点	是
下拉选择	是
用户正在拖动的面板	是
动态数值和进度条	按快照更新

这项修改不仅能解决当前星系折叠问题，也应该推广到市场、殖民地、科研、外交和事件管理等管理视图。

3.5 问题五：登陆行星地表后出现永久软锁
P0：最高优先级的状态机缺陷
我认为这是八个问题中最严重的一个。

它不是单纯的返回按钮遗漏，而是多个模块间的接口契约没有接起来。

当前路径大致是：
银河
  ↓
星系
  ↓
选中行星
  ↓
设置 app._groundTargetPlanet
  ↓
goto('ground')
  ↓
GroundView


问题出现在最后两步。
第一处问题：目标行星没有形成明确的路由参数
星系视图的行星卡片设置：
app._groundTargetPlanet = p.id;
app.goto('ground');


但是 GroundView 的构建逻辑并没有消费这一字段。

换句话说，目标行星被暂时放在 App 的一个普通属性中，却没有成为地表视图的正式输入参数。

这意味着地表视图并不知道自己到底应该围绕哪颗行星构建简报。
第二处问题：简报可选项只面向已有殖民地
当前 GroundView 的简报下拉选项，主要来自玩家已经拥有的殖民地。

没有殖民地时，会出现：
尚无玩家殖民地——先在星系视图建立前哨站。


这本身并非错误提示。

真正的问题是：

玩家已经通过行星卡片点击了“登陆行星地表”，但系统却没有建立一个适用于未殖民行星的地表行动模式。
第三处问题：简报没有返回按钮
目前简报状态使用：
_setHead('简报', []);


按钮列表为空。

这使得玩家在没有可执行任务时，无法通过当前页面正常返回。

而且 GroundView 的 Escape 处理主要针对 free 模式，不会为无任务的 briefing 模式提供可靠的退回操作。
第四处问题：全局检视器生命周期没有跟随路由切换
App._onRoute() 调用 activateView() 切换视图，但是没有建立统一的路由切换后检视器清理策略。

旧视图留下的全局选中实体状态和右侧 Inspector 可能继续显示。

这就是为什么从星系页面直接进入地表时，旧的恒星信息面板还会残留。
正确修复应该是四件事一起做
子系统	应该修改的契约
Route	跳转时明确传入 planetId、entryMode、returnRoute
GroundView	必须消费目标行星 ID，不能从全局临时属性猜目标
Inspector	进入地表时执行明确的隐藏或重新绑定策略
Navigation	任意简报状态都必须拥有有效返回路径

例如，地表路由应该具备类似下面的状态：
{
  screen: 'ground',

  params: {
    planetId: 'planet_xxx',
    entryMode: 'survey'
  },

  returnRoute: {
    screen: 'system',
    params: {
      systemId: 'sys_396'
    }
  }
}


这是示意结构，具体编码方式可以与现有 hash router 保持一致。
更重要的是：必须新增“未殖民行星探索”模式
应该把以下两类地表活动分开：
模式	进入条件	可执行活动
survey 先遣勘探	目标行星可登陆或有相应探索入口	地形调查、矿脉勘察、遗迹采样、环境分析
mission 正式行动	有可执行的战术任务	救援、破坏、护送、Boss 战、战斗撤离

没有殖民地，不应该等于没有任何理由登陆行星。

实际上，探索和殖民之间应该形成一种因果关系：
首次发现行星
    ↓
轨道扫描
    ↓
先遣地表勘探
    ↓
确认矿脉、环境、危险和遗迹
    ↓
判断殖民价值
    ↓
建立前哨
    ↓
形成正式殖民地


这比“先建立殖民地才能进入地表”更合理。

玩家应该能够先了解一个地方，才决定是否值得在这里投入长期资产。

产品任务书把行星行动列为核心玩法之一，同时要求关键操作具备明确阻断原因与返回能力。当前行为明显偏离这一目标。

3.6 问题六：事件触发后不知道应该去哪里
P1：任务系统与空间世界连接不足
当前的问题不是事件描述写得不够长。

而是事件模型尚未区分两类本质不同的事件。
A 类：叙事决策事件
例如：
- 外交官遭遇利益诱惑。
- 某个组织提出资源交易。
- 内部派系发生争执。
- 是否接受某项政策或协议。
这类事件本身不一定需要地图目标。
B 类：空间运营事件
例如：
- 商船队在某条航路遭袭。
- 某星系的空间站受到攻击。
- 一支友方舰队陷入包围。
- 一个深空信号正在逐渐消失。
- 某颗殖民行星发生灾害。
这类事件必须包含空间定位和行动目标。

我检查了当前的 evt_pirate_raid。

它的事件正文大意是：
一支无旗籍劫掠舰队出现在边域航路，袭击了孤立商队。

但实际选项主要是：
- 花费 400 信用点组织护航联盟，设置一个标志。
- 扣除 250 信用点，让商队自行规避。
它没有明确的 targetSystemId、targetLaneId，也没有可执行的空间任务目标。

因此现在的“航线劫掠”更接近一条经济决策事件，而不是一个真正发生在某条具体航路上的可操作事故。

这正是用户所感受到的断层。
建议：事件与任务目标分离
建议建立独立的 WorldObjective 或类似的任务目标实体。

例如：
{
  id: 'objective_raid_001',

  sourceEventId: 'evt_pirate_raid',

  kind: 'escort_convoy',

  target: {
    kind: 'lane',
    id: 'lane_123'
  },

  status: 'active',

  deadlineTick: 12000,

  priority: 'high',

  assignedFleetId: null,

  progress: 0
}


这一层不必完全复制传统 RPG 的任务系统，但至少需要让事件能够真正进入世界模拟。

地图需要提供：
- 事件目标 Pin。
- 目标星系或航路高亮。
- 目标离屏方向指示。
- 点击事件直接聚焦镜头。
- 显示建议舰队。
- 显示 ETA、燃料、航路风险。
- 一键生成派遣或护航指令。
- 任务成功或失败后有明确反馈。
我尤其建议增加一个当前任务追踪条。

它不应只是历史通知，而是玩家当前准备采取行动的地方。

3.7 问题七：每个星系似乎只有两个星球
P1：需要进一步区分生成数据与视觉呈现
这个问题不能直接认定为生成器硬限制。

因为当前 galaxyGen.js 中存在：
const nPlanets = RNG.intRange(world, 2, 8);


而 RNG.intRange() 是闭区间随机整数。

也就是说，当前实际生成数量是：
\[
N_{\text{planets}}\in\{2,3,4,5,6,7,8\}
\]

不是固定为 2。

而且 SystemView._buildData() 将 sys.planetIds 中的行星全部映射进视图数据；System3D 也按照行星数组逐个计算轨道和渲染数据。

当前代码中没有发现统一把星系行星列表截断为 2 个的逻辑。

因此：

不能仅凭当前主分支源码判断 sys_396 实际有多少颗行星，也不能把“2 个星球”直接归因于生成器。

目前还缺少该存档的世界种子、sys_396 实际生成数据以及玩家屏幕截图。

但已经能够发现另外一个更重要的问题：

当前生成器主要创建的是 planets 实体，并未在这段生成流程中建立完整的月球、卫星和小行星带实体体系。

也就是说，项目中虽然可能存在 2–8 颗主要行星，但星系的整体天体组成仍然比较单薄。
我的建议：不要简单地把所有星系改为 8 颗行星
应当把星系建模从“行星数量”升级为“天体构成”。

建议：
天体类型	应承担的玩法价值
主恒星	能源、辐射、轨道环境、异常
岩质行星	地表探索、矿脉、殖民
海洋行星	水资源、生物、生态科研
冰封行星	冰层矿脉、地下海洋、极端环境
气态巨行星	氢、氦-3、风暴、浮空采集平台
卫星	稀有矿脉、独立殖民、地表行动
小行星带	矿业、采矿舰、资源运输
彗星或特殊天体	周期性事件、稀有资源、探索

实际生成目标可以继续以产品任务书中的 2–8 个主要行星为基线，再扩展卫星和小行星带；该任务书本身也规划了 2–8 个天体的首期规模，以及包括卫星、小行星带在内的进一步扩展。
VOID_FRONTIER_星际游戏长线研发任务书.md

我建议再做一个固定种子的批量统计：
- 生成 1000 个以上种子。
- 统计各星系实际行星数量。
- 统计恒星类型与行星数量关系。
- 统计 2、3、4、5、6、7、8 颗行星的频率。
- 统计轨道最外层行星是否超出视口。
- 统计轨道间距和行星重叠情况。
- 直接读取当前存档中的 sys_396 数据。
这样才能明确区分：
1. 随机种子恰好生成了两个。
2. 其他行星还没有在调查情报中显示。
3. 行星已经生成但视觉上不可辨认。
4. 轨道布局导致外层行星被误认为不存在。

3.8 问题八：行星地表内容严重不足
P1：核心玩法深度不足
这是一个产品级问题，比单纯的 UI bug 更值得长期投入。

但需要准确描述现状。

我检查到当前 SurfaceSandbox.js 已经具备：
- 64×24×64 的体素世界。
- 4×4 分块结构。
- 8 类行星地形参数。
- Simplex 噪声地貌。
- 地下洞穴雕刻。
- 基于行星矿藏生成的矿脉。
- 确定性地表生成。
这说明项目已经有实际的地表技术基础。

另外，missions.js 中已经存在八种地面任务模板：
任务	主要玩法
遗迹调查	数据核心回收
救援失踪人员	搜寻与救援
摧毁防空节点	战斗与破坏

深渊体遭遇	Boss 战与撤离

因此，这里不是完全没有地表内容。

真正的问题是：

现有地表内容主要体现为离散任务实例，而不是玩家可以在大量未殖民行星上持续发现、调查、利用和记录的探索世界。

任务模板已经存在，但前殖民期探索没有形成充分的玩法入口和持续发现机制。

这就造成了一个非常明显的体验问题：

玩家俯瞰银河，看到许多看似可以探索的星球，进入之后却发现它们大部分只是拥有一组环境参数和矿藏数字。

这容易让玩家产生“宇宙很大，但内容很少”的感觉。

四、行业标杆对照：你真正需要借鉴的是操作体系，而非美术或题材

这是两种不同的产品气质。

4.2 这八款游戏背后的共同点
它们看似完全不同：
- WoW 是 MMORPG。
- Stonehearth 是殖民经营。
- Terraria 是动作沙盒。
- KSP 是航天模拟。
- Planetbase 是生存建造。
- Astroneer 是探索创造。
- shapez 是工厂物流。
- DSP 是星际工业自动化。
但它们在交互层面有一个非常重要的共同点：

玩家能够直接对游戏世界中的对象采取动作，而且动作结果可预测、可观察、可追踪。

而 VOID FRONTIER 目前的问题恰恰是，这条链经常断掉。

例如：
玩家意图	理想的游戏响应	当前暴露的问题
我想去这个星球	直接聚焦或进入行星界面	只能选中，需要额外寻找面板操作
我想处理这次劫掠	地图标记目标，显示舰队行动方案	只给出文本和经济选项
我想看看这个星球有什么	可以登陆、探索、扫描 POI	未殖民星球无法自然进入先遣探索
我想展开这个情报模块	模块保持展开并正常显示	快照重建后状态丢失
我想返回上一级	有明确返回按钮和状态恢复	地表简报可能没有有效返回路径
我想建立生产线	看得到输入、输出、物流和瓶颈	现有经营数据还需要加强可视化

这不是美术问题。

这是交互协议的问题。

五、我建议建立统一的四层游戏操作体系
这是我认为对长线研发价值最高的架构性建议。

当前产品任务书已经规划了银河地图、星系详情、行星/殖民地、战斗、舰队、科研、事件和行星行动等页面，但这些页面尚未完全形成一致的操作语法。
VOID_FRONTIER_星际游戏长线研发任务书.md

我建议将所有玩家行为统一归纳为四层。
L1 · GALACTIC STRATEGY
银河战略层

世界地图、势力边界、星系控制、文明关系、贸易网络、战争前线。

对应：Stellaris、Paradox 大战略、WoW 世界地图式任务定位。


L2 · SYSTEM OPERATIONS
星系空间层

恒星、轨道、行星、卫星、空间站、航道、舰队和异常。

对应：EVE 的空间运营、KSP 的计划与预演。


L3 · PLANETARY SANDBOX
行星经营与探索层

地表勘探、POI、殖民地、建筑、采矿、资源物流、环境和灾害。

对应：Planetbase、Stonehearth、Astroneer、DSP。


L4 · TACTICAL ACTION
局部战术行动层

角色、装备、地形、采集、救援、战斗、交互、撤离。

对应：Terraria 的直接操作和动作游戏的任务执行。


关键不是这四层页面的数量，而是必须支持无断点导航。

例如：
银河发现异常信号
    ↓
点击事件定位
    ↓
进入目标星系
    ↓
选择信号附近的行星
    ↓
查看行星环境和 POI
    ↓
派遣探索舰或登陆小队
    ↓
获得样本、遗迹数据或资源
    ↓
科研 / 工业 / 外交产生变化
    ↓
回到银河层


这才是你希望的长期沙盒体验。

每一层都应该能够回答三个问题：
1. 我现在在哪里？
2. 我能对眼前的对象做什么？
3. 我完成当前操作之后，应该如何继续？

六、行星内容重构：从“行星参数列表”升级为“可探索的世界”
我认为这是项目中长期价值最高的一项玩法投资。

现有行星实体拥有：
- 行星类型。
- 重力。
- 温度。
- 大气。
- 辐射。
- 水储量。
- 资源矿藏。
- 宜居度。
- 开发上限。
这些属性可以描述行星，但不能独立构成有趣的行星。

一个真正具有探索价值的行星，至少需要四个维度：
\[
PlanetValue =
PhysicalIdentity +
ExplorationContent +
OperationalUtility +
NarrativeIdentity
\]

也就是：
- 物理特征。
- 探索内容。
- 经营价值。
- 独特叙事。
6.1 新增持久化 POI 系统
建议为每颗行星建立独立的 POI（Point of Interest）系统。

可以包括：
POI 类型	玩法	可能奖励
古代遗迹	考古调查	Ancient Data、科技
坠毁飞船	残骸打捞	合金、模块、飞船蓝图
深层矿脉	地质勘探	稀有矿物
生物痕迹	生态采样	生物质、生态科技
异常磁场	仪器测量	传感器技术、异常数据
失联研究站	人员救援	船员、科研资料
地下洞穴	地形探索	地下矿藏、未知遗物
气候灾害区	环境采样	特殊材料、气候研究

建议 POI 至少具有如下数据字段：
{
  id: 'poi_001',

  planetId: 'planet_001',

  kind: 'ancient_ruin',

  discoveryState: 'hidden',

  threatLevel: 2,

  explorationProgress: 0,

  rewards: [
    {
      resourceId: 'ancientData',
      amount: 4
    }
  ],

  seed: 123456
}


这是一个概念结构，实际实现时还应明确：
- POI 的生成条件。
- 是否需要轨道扫描。
- 是否需要地表行动。
- 是否存在危险和消耗。
- 是否允许重复访问。
- 是否允许重复发奖。
- 发现记录如何进入存档。
- 是否影响其他系统。
POI 最重要的特征：必须持久化
它不能只是每次进入地表随机生成一处遗迹。

如果玩家今天发现了一个古代遗迹，明天重新进入该星球时，遗迹应该仍然在那里。

如果玩家已经回收了数据核心，重新进入也不能无限领取。

否则世界没有记忆，所有探索都会退化为一次性资源刷新。

6.2 先遣探索必须拥有一个低门槛循环
建议玩家开局就能执行最基本的先遣勘探。

例如：
示例：未殖民冰封行星的首次探索







seeles.ai


1. 轨道扫描
   
   发现冰层下方存在异常密度结构。
2. 派遣科考小队

3. 着陆后调查

5. 科研反馈
   
   解锁相关研究或修正星球资源评价。

十一、我认为最应该避免的四种研发误区
11.1 不要把增加行星数量当作解决内容空洞的主要方法
如果一个星系有 8 颗行星，但每颗行星都只是：
- 不同颜色。
- 不同重力。
- 不同资源数字。
- 不同宜居度。
那么玩家很快还是会感觉无聊。

真正有意义的是每颗行星具备不同的行动机会。

一个具有遗迹、失联研究站、深层矿脉和异常生物的冰封行星，可能比十颗只有资源数字差异的行星更有价值。
11.2 不要把所有界面都做成复杂管理面板
你同时参考了 Terraria、Astroneer 和 KSP。

这意味着必须保留直接操作的自由度。

例如：
- 地表应允许直接点击和操作目标。
- 行星应允许直接聚焦和查看。
- 舰队应允许通过空间目标下达命令。
- 工业系统应允许直观查看物料流向。
不要把所有操作都藏在多个 Tab、按钮和二级弹窗中。
11.3 不要过早追求零 GC、极限 FPS 或更复杂的 WebGL 特效
项目目前的核心问题不是恒星粒子不足，也不是少数临时对象没有池化。

这些工作当然有价值，但从玩家体验影响看：
- 无法正常返回。
- 面板自动折叠。
- 不能直接前往行星。
- 无法找到事件目标。
- 不能进入未殖民行星。
显然比高倍速下偶发的内存回收停顿更紧急。

因此应先修复 P0，再做深度性能优化。
11.4 不要以页面数量代表系统完整度
新增一个地表探索页面，并不意味着地表探索系统已经完成。

真正完整的功能必须包含：
进入条件
  ↓
合法目标
  ↓
操作输入
  ↓
领域命令
  ↓
世界状态变化
  ↓
事件反馈
  ↓
存档持久化
  ↓
返回 / 继续


少任何一环，都可能只是一个看起来完整的 UI。

十二、最终结论：VOID FRONTIER 应该走向什么样的产品？
我认为项目不应该只是向《群星》或 EVE 的方向继续扩张。

它应该形成一个更有特色的组合：
维度	推荐的核心方向
银河战略	Stellaris / Paradox
星际航行	EVE / KSP
舰队战斗	StarCraft 的战术可读性
殖民地经营	Stonehearth / Planetbase
地表探索	Terraria / Astroneer
工业生产	Shapez / Dyson Sphere Program
人物行动	动作 RPG
叙事事件	Paradox 式世界事件和分支决策

但它们不应成为互不相关的玩法拼盘。

它们必须被统一的世界模型和资源流连接起来。

例如：
- 地表发现一种稀有材料，应该影响工业科技。
- 建立矿业殖民地，应该改变贸易航线和舰队补给。
- 一场空间劫掠，应该影响运输、经济、外交和战争。
- 一次地面 Boss 战，应该改变某个行星的控制权或者释放某种科技。
- 发现一个古代遗迹，应该推动文明事件链和银河级剧情。
这才是这个项目最有潜力的地方。
12.1 当前真正的第一目标
我会把下一个产品里程碑定义为：
VOID FRONTIER · PLAYABLE FRONTIER
建议的下一阶段产品里程碑

玩家可以从银河地图出发，自然地选择星系、进入行星、完成未殖民行星探索、建立前哨、开始生产，并能通过事件和地图指引继续执行任务。

必须完成的体验闭环
1. 空间层级导航可靠。
2. 任何页面都能正常返回。
3. 重要事件具备明确行动目标。
4. 未殖民行星具有可探索内容。
5. 探索结果能影响科研、资源和殖民决策。
6. 所有状态都能正确保存和恢复。

这个里程碑不要求立即完成所有文明、所有舰船、所有 POI 或所有工业设施。

但必须证明：从一个陌生星系开始，玩家能够经历一次有意义的探索、发现、行动和发展。
12.2 最终评级
方向	我的结论
是否值得继续投入？	是，底层架构有较好的复用价值
是否需要重写核心引擎？	不建议
是否需要重构部分 UI 生命周期？	是，尤其是导航、快照和 Inspector
是否应该增加更多行星？	应该，但必须同时扩展天体组成和玩法内容
是否应该扩展地表？	是，优先补前殖民期探索和持久化 POI
是否应该扩展工业？	是，但排在 P0 之后

当前最重要的工作	修复交互闭环，并建立第一个真正完整的行星探索循环

我的最终判断：这个项目不缺少一个漂亮的技术底座，它缺少的是让玩家能够持续利用这个底座的完整交互和内容体系。

目前已经能够看到一个相当有潜力的星际模拟世界，但玩家还需要更直接地进入它、探索它、建设它、改变它。

下一步最值得做的，是把本报告的 P0 项整理成一份可直接交给自主研发 Agent 执行的修复规格，并为每项缺陷配套浏览器级验收测试。
