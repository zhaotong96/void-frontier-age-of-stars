### 三、 穿透式源码取证：十大核心缺陷深度剖析（P0–P2）

#### 【P0-A】`GroundView.js` 半截子 `site_meters` 改造导致全任务实体渲染坐标与撤离罗盘全量 `NaN`（实机隐形与战斗瘫痪）

* **取证位置**：[GroundView.js](https://drive.google.com/open?id=[REDACTED]) 第 `2188–2215` 行（`_emitMissionStrike`）、第 `2481–2538` 行（`_assembleRenderData`）、第 `2546–2570` 行（`_bmeshList`）、第 `2811–2820` 行（`_drawHudMission`）。
* **机理与数学证明**：
* 在 [GroundMission.js](https://drive.google.com/open?id=[REDACTED]) 第 `851–890` 行切换为 `coordSpace: 'site_meters'` 后，任务实体不再生成 2D 网格，`mission.w` 与 `mission.h` 均为 `undefined`，单位与目标的 `(x, y)` 已经是 Planet-Local 米制坐标（范围 `[-256, +256]`），且 `mission.extraction` 结构为 `{ x, z, r }`（注意纵向键名为 `z` 而非 `y`）。
* 然而，执行工程师在修改 [GroundView.js](https://drive.google.com/open?id=[REDACTED]) 时，**仅仅在 `_setupScene`（第 975 行）和 `_followMissionCharacter`（第 1706 行）两处为玩家主控角色写了 `m.coordSpace === 'site_meters'` 分支**，其余 4 个核心渲染与 HUD 函数全部原封不动保留了旧版像素换算公式：
```javascript
const kx = SURFACE_SIZE.X / (m.w * TS); // 64 / (undefined * 24) === NaN !
const kz = SURFACE_SIZE.Z / (m.h * TS); // 64 / (undefined * 24) === NaN !

```


* **实机后果（已在 Node.js 加载 bundle 实测证实）**：
1. **全场敌军、队友、NPC 100% 隐形**：`_assembleRenderData`（第 2486、2517、2528 行）计算 `ex = e.x * kx = NaN`，传入 WebGL 实例缓冲后所有敌军、小队队友、救援工程队顶点全部变成 `NaN` 被 GPU 丢弃，玩家在画面上看不见任何敌人或队友，却在空气中被隐形敌人围殴致死！
2. **全部任务目标物与数据核心 100% 隐形**：`_bmeshList`（第 2550、2563 行）计算 `tx = t.x * kx = NaN`、`ix = it.x * kx = NaN`，摧毁目标建筑与拾取核心在 3D 场景中完全不显示。
3. **刀光与远程射击光束 100% 消失**：`_emitMissionStrike`（第 2190 行）计算 `wx = u.x * kx = NaN`，攻击无任何视觉特效。
4. **HUD 顶部撤离罗盘彻底损坏并显示 `撤离区 NaNm**`：`_drawHudMission`（第 2813–2814 行）计算 `ex = view.extraction.x * kx = NaN`，且访问了 `view.extraction.y`（在 `site_meters` 下 `extraction` 只有 `.z` 没有 `.y`，即便修好 `kx` 也是 `undefined`），导致顶部罗盘箭头旋转角 `rel = NaN`，文字直接渲染出 `撤离区 NaNm`。





#### 【P0-B】`mission.field` 挂载进 `world.entities.groundMissions` 引发 97MB 存档爆炸、24MB 导入熔断与读档即崩

* **取证位置**：[GroundMission.js](https://drive.google.com/open?id=[REDACTED]) 第 `882` 行（`mission.field = field;`）、[SaveCodec.js](https://drive.google.com/open?id=[REDACTED]) 第 `13–24` 行、[commandBus.js](https://drive.google.com/open?id=[REDACTED]) 第 `94` 行。
* **机理与实测数据**：
* [规范 1](https://drive.google.com/open?id=[REDACTED]) 第 2.5 节与 [GroundMission.js](https://drive.google.com/open?id=[REDACTED]) 文件头明确规定：“任务实体是纯数据（Plain Data），挂在 `world.entities.groundMissions` 上，全部状态可 JSON 序列化；undefined 与函数不得进入世界状态。”
* 执行工程师在 `createGroundMission` 第 `882` 行直接执行了 `mission.field = field;`，把包含 **64 个区块（每个区块 65×65 顶点的 `position`、`normal`、`tangent`、`materialWeights`、`aux`、`indices` TypedArray 缓冲）以及 `evalPoint`、`siteModifier`、`_macro` 闭包函数**的巨型运行时地形场直接挂进了 `world.entities.groundMissions[id]`！而且任务结束后 `mission` 仍留在 `groundMissions` 字典中供历史记录读取，永不释放。
* **三重致命后果（Node.js 实测证实）**：
1. **存档体积暴涨至 96.99 MB，突破 24MB 硬上限**：仅创建 **1 场**地面任务后调用 `encodeSave(world)`，耗时高达 **6,243 ms**（主线程卡死 6.2 秒），生成的 JSON 字符串长达 **101,703,014 字节（96.99 MB）**！调用 `decodeImported` 时直接触发 `MAX_IMPORT_BYTES = 24MB` 限制被拒绝（`{ ok: false, reason: '文件超出大小上限' }`），同时撑爆浏览器 `localStorage`（5MB 限额）。
2. **读档后地面任务立即崩溃**：即便从 IndexedDB 读取存档，反序列化后的 `mission.field` 已丢失所有函数属性（`typeof m.field.evalPoint === 'undefined'`，`typeof m.field._macro.heightAt === 'undefined'`），且 `Float32Array` 退化为普通对象 `{ "0": ..., "1": ... }`。一旦恢复任务移动或发射视线射线，立即抛出 `TypeError: field.evalPoint is not a function`！
3. **命令总线每次执行卡顿 1.4~1.6 秒**：`commandBus.js` 第 `94` 行在每次玩家或 AI 执行命令前都会调用 `const snapshot = deepClone(world);`。一旦 `world.entities.groundMissions` 里挂着 `mission.field`，后续每一次命令（包括 AI 每小时的建造、科研、移动命令）都会深拷贝 64 个网格区块，单次 `executeCommand` 耗时从 `2ms` 暴增至 **`1,413ms ~ 1,639ms`**！
